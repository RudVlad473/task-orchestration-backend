<objective>
Add OpenTelemetry tracing to the app so one request is one trace across the HTTP handler, the async Kafka publish and the activity consumer, with trace ids in the JSON logs, at 100% sampling controlled by a property, and with probe and scrape noise suppressed.

Purpose: D-08 and the "one request, followed end to end" half of the phase. The two code fixes here are required: the hand-built @Primary KafkaTemplate bypasses Boot's template observation property, and the @Async hop drops the trace context (both proven in the research scratch worktree by removal).
Output: tracing dependencies, properties, two Kafka/async fixes and two tests; the code fixes and the log/security cases fail without their change, and the management-port case characterises Boot. Export stays off until the Tempo plan sets the env.
</objective>

<data_flow>
Boot's HTTP observation starts a span per request and puts traceId/spanId in the MDC, which the ECS formatter writes as JSON fields. The after-commit listener hops to kafkaPublishExecutor; the TaskDecorator restores the context there, so the observed KafkaTemplate creates a PRODUCER span and writes a traceparent header on the record. The listener container's observation reads that header and starts the CONSUMER span as its child; spans leave the pod over OTLP/HTTP only when export is enabled.
</data_flow>

<approaches>
| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Micrometer Tracing OTel bridge + OTLP exporter, template observation set on the hand-built bean, ContextPropagatingTaskDecorator on the async pool (research Pattern 3, verified end to end) | Pro: Boot-native; two small code changes; trace ids in logs for free. Con: two new runtime artifacts and a test artifact | Verified working in the scratch worktree |
| B. OpenTelemetry Java agent (-javaagent) | Pro: zero code, wide instrumentation. Con: changes the Docker image and JVM flags, bypasses Micrometer Observation (business Observations would not join), larger memory | Rejected: heavier and separate from the Observation API the business timers use |
| C. Manual traceparent header handling in KafkaEventPublisher and the listener | Pro: no observation config. Con: hand-rolled propagation, easy to break | Rejected (research Don't Hand-Roll) |

Non-obvious trade-offs:
- Adding `spring.kafka.template.observation-enabled` would do nothing here (the @Primary template is hand-built); it is deliberately not added.
- No ObservationPredicate is added. Claude review finding 04 measured, on a live bootRun, more than 15 management-port requests producing zero http_server_requests observations: Boot does not observe the management child context, so scrapes and probes already produce neither spans nor http_server_requests series, and a predicate cannot change either. The main-port /api/actuator paths that do get observed are the 401 scanner signal 14-04 counts as auth failures; hiding them would lose data. The test pins the management-port fact so a Boot upgrade that starts observing it fails loudly.
- Tests: @SpringBootTest disables tracing propagation unless the class carries @AutoConfigureObservability; without it the traceparent header stays empty and the tests would chase a ghost.
- An incoming traceparent header from a client is honoured; trace ids are not security tokens, so this is accepted.
</approaches>
