<objective>
Authorise the fault-injection scope for the whole measurement run, then fire every detection alert once on purpose, in nonprod unless authorised otherwise, and record time-to-notification for each.

Purpose: the phase ends in a measurement (CONTEXT specifics: the résumé bullets are written from these numbers), and D-15's backup alert gets a number from this cluster. The pipeline pages (dead-man, uptime, Flux), the app memory re-measure and the runbook section follow in 14-11; the measurement was split in two so each executor stays inside the context budget.
Output: a per-row measurement table in this plan's SUMMARY.md, the scratch evidence files, and a cluster back to its committed state.
</objective>

<data_flow>
Each injection changes something Prometheus observes (a scaled-down Deployment, a blocked scrape, a poison record, a lowered scratch threshold over a real metric). The alert then travels the path plans 14-06 and 14-08 built: rule evaluation, Alertmanager grouping, Telegram. The agent timestamps the fault and reads Prometheus and Alertmanager counters through the apiserver proxy; the operator reads the receipt time in Telegram.
</data_flow>

<approaches>
| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Real injections where they are non-destructive in nonprod, scratch rules with lowered thresholds on real metrics where they are not, each labelled (research measurement table) | Pro: honest numbers for detection plus routing; prod untouched by default. Con: substituted rows measure routing, not the production threshold | Recommended at Task 1 |
| B. Add one real prod injection (prod app scaled to 0) | Pro: one true production time-to-notification. Con: about ten minutes of public prod outage | Offered at Task 1 |
| C. Fire synthetic alerts straight into Alertmanager's API | Pro: fast. Con: skips rule evaluation and `for:` timing, so it measures nothing about detection | Rejected (used only as the routing check in plan 14-06) |

Non-obvious trade-offs:
- Telegram's client shows receipt time to the minute; the Alertmanager notification counter gives a machine bound at the scrape interval. Both are recorded; neither is presented as more precise than it is.
- A poison record in nonprod lands in the nonprod dead-letter topic; nonprod is resettable by design.
- Rows run one at a time, each waiting for the previous alert to resolve, so the notification counter attributes cleanly; this is why the run is long and why the pipeline tests moved to 14-11.
</approaches>
