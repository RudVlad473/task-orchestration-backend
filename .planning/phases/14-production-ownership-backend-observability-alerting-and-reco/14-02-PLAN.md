<data_flow>
The script runs in a pod next to Postgres: pg_dump writes a custom-format archive to an emptyDir, pg_restore -l proves the archive's table of contents is readable, and age encrypts it to the public recipient. aws s3api put-object sends the encrypted file to B2 over TLS with a key that can write but never read or delete. B2 applies Object Lock and the lifecycle rules; the private key needed to read a dump never leaves the operator's password manager.
</data_flow>

|---|---|---|
| A. Retention by B2 lifecycle rules (S3 PutBucketLifecycleConfiguration, applied once with an admin key) plus bucket-default Object Lock (recommended by research) | Pro: the VM key never needs delete; rules are versioned JSON. Con: the S3 lifecycle API is only supported since 2025-12 and must be applied by a human with an admin-capable key | Satisfies D-12 (write-only VM key) and D-13 (lifecycle where the S3 API supports it, confirmed supported) |
| B. Retention enforced by the job (list and delete old objects) | Pro: no lifecycle API. Con: the VM key would need listFiles and deleteFiles, which D-12 forbids | Rejected: contradicts D-12 |
| C. rclone instead of aws s3api put-object | Pro: one binary, sync semantics. Con: rclone's existence probes (HEAD/list) are untested against a write-only key | Rejected: put-object is exactly one PutObject call the key is allowed to make |

Non-obvious trade-offs:
- A write-only B2 key still has b2_hide_file through writeFiles: once a file's lock expires, a stolen key can hide it, and the lifecycle then deletes the hidden version a day later. The effective protection window equals the Object Lock retention; Task 1 states this per option.
- `[ "$(date -u +%u)" = 7 ] && ...` as the script's last line makes every non-Sunday run exit 1 under set -e; the weekly branch must be an if/fi block, and the smoke test runs both branches.
- aws-cli 2.23+ sends CRC64NVME checksum headers by default; the CronJob pins AWS_REQUEST_CHECKSUM_CALCULATION=when_required and AWS_RESPONSE_CHECKSUM_VALIDATION=when_required.
- The prod dump was 103,928 bytes at cutover: single PutObject, no multipart, far inside the free 10 GB.
</approaches>

  <decision>Object Lock mode and default retention for the backup bucket, and whether weekly copies get a longer per-object lock.</decision>
  <context>
What is at stake: Object Lock is what stops a stolen VM key from destroying backups. Enabling it on a bucket can never be turned off, and compliance-mode retention cannot be shortened or removed by anyone, the account owner included. That is the one-way door.

What the research found (Backblaze docs, not exercised live): the default retention is bucket-wide and applies to files uploaded after it is set. A web-UI key restricted to one bucket gets no Object Lock capabilities, so its uploads simply inherit the bucket default. The write-only key can still hide a file (writeFiles includes b2_hide_file); after a file's lock expires, a hide plus the lifecycle's 1-day delete of hidden versions removes it. So the lock length is the window in which backups survive a compromised VM. Lifecycle deletion of a still-locked file fails, so retention must not exceed the lifecycle age (7 days for daily/).

Cost of each option:
- option-a, governance 7 days: every file is undeletable for 7 days; the account owner can still override with bypassGovernance. Weeklies older than 7 days are protected only by the key's lack of delete. Web-UI key, simplest setup.
- option-b, governance 7 days plus weekly copies locked 28 days per object: the VM key must be created with the B2 CLI or API (not the web UI) with writeFiles and writeFileRetentions; the script passes --object-lock-mode GOVERNANCE and a retain-until date 28 days out on weekly uploads. Weeklies survive a compromised VM for their whole life. One more capability on the VM key (it can set, not shorten, governance retention).
- option-c, compliance 7 days: like option-a, but not even the account owner can delete a file early, which also protects against a stolen B2 account login. A mistaken upload cannot be removed for 7 days.

Reversibility: one-way (Object Lock cannot be disabled; compliance cannot be undone).

Recommendation: option-a. It meets D-12's intent with the least setup, and the 26-hour missing-backup alert plus a 7-day window bounds the damage of a VM compromise. Pick option-b if losing weeklies to a compromised VM matters more to you than one extra key capability.

If you say nothing: no auto_select; the plan waits.
