<objective>
Measure the three pages that do not go through rule evaluation (the healthchecks.io dead-man, the uptime workflow, the Flux deploy failure), re-measure app memory a day after tracing went live, and write the whole measurement, 14-10's detection rows included, into the runbook.

</objective>

<data_flow>
Stopping Alertmanager halts the Watchdog's pings, so healthchecks.io, outside the VM, pages Telegram on its own. A dispatched uptime run with a failing URL posts to Telegram from GitHub Actions. An unpullable image tag pushed to the nonprod overlay makes apps-nonprod's `wait` time out, and notification-controller posts the error event to the muted chat. The agent timestamps each fault and reads healthchecks.io, the workflow log and the Flux events; the operator reads the receipt time.
</data_flow>

<approaches>
| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Real pipeline faults in a bounded window, each reverted in the same session, under 14-10's authorisation | Pro: the only way to time paths that bypass Prometheus. Con: 15-20 minutes with no Alertmanager paging; one bad commit and its revert in history | Authorised at 14-10 Task 1 |
| B. Point the uptime probe at a fake URL only, skip the dead-man and Flux tests | Pro: no paging gap, no bad commit. Con: D-06's 10-15 minute dead-man estimate and the post-deploy todo stay unmeasured | Rejected: those two are the numbers this plan exists for |
| C. Measure the dead-man by pausing the healthchecks.io check | Pro: no cluster change. Con: tests healthchecks.io's notification, not the Watchdog-to-webhook path | Rejected |

Non-obvious trade-offs:
- Stopping Alertmanager silences all paging for about 15-20 minutes; run it when nothing else is being measured.
- ImageUpdateAutomation must be suspended during the bad-tag test, or it rewrites the tag back to the policy's latest within 5 minutes and the failure never reaches the `wait` timeout.
- The memory re-measure needs 24 hours of tracing traffic after 14-09's export; if that window has not elapsed, Task 2 waits rather than reading a shorter window.
</approaches>
