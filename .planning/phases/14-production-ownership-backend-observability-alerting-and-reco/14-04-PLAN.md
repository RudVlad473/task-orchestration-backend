<objective>
Make the app count the decisions it already takes on the request path (tasks created and moved, optimistic-lock conflicts, ownership denials, auth failures), log auth and access-control failures as structured JSON events, switch console logs to ECS JSON in UTC, and time the four hottest endpoints, three of them with a service-level Observation.

Purpose: these are series the alert rules and the Phase 14.1 dashboards read. Closes two folded todos: security-event logging on auth and access control, and the structured/UTC-logging half of the remote-logging todo. The Kafka counters, the latency buckets and the exact-name scrape contract follow in 14-05, which was split out of this plan to keep each within the context budget.
Output: counters and timers with tests at the HTTP layer they live in, PII-free JSON security events, and ECS console logs.
</objective>

<data_flow>
Each hook point (an exception-handler arm, the authentication entry point, a service method) increments a Micrometer counter registered at startup in the shared MeterRegistry; the Prometheus registry renders those counters on the management port as kanban_*_total series. The same handler arms emit one WARN line through SLF4J's key-value API, which the ECS formatter turns into JSON fields. Boot's http.server.requests observation already times every request per templated uri; the three service Observations add a timer (and, once 14-07 lands, a span) around the service method.
</data_flow>

<approaches>
| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Counters at the existing choke points (GlobalExceptionHandler arms, entry point, service methods) registered eagerly; Observation API around the hot service methods; Boot's per-uri http.server.requests timer for every endpoint (research Finding 2, no new dependency) | Pro: one hook per decision; no AOP; names in one constants class. Con: handler and services gain a MeterRegistry field | Matches research Finding 2 and the project's field-injection convention |
| B. @Timed/@Observed annotations with spring-boot-starter-aop | Pro: declarative. Con: new dependency; @Timed on controllers duplicates http_server_requests | Rejected and recorded in must_haves: the per-endpoint timer already exists; the value is the service-level timer and span |
| C. Derive everything from logs in Loki (LogQL metrics) | Pro: no code. Con: slower, label-poor, couples alerts to log wording | Rejected |

Hottest endpoints (CONTEXT Claude's Discretion, chosen from RESEARCH "Hottest endpoints (3-5)"): GET /api/boards/{boardId}/full (BoardController.findFullById, the one nested board document every page load fetches), POST /api/boards/{boardId}/columns/{columnId} (ColumnController.addTaskByColumnId, task create), PATCH /api/tasks/{taskId}/move (TaskMoveController.moveToColumn, about 9 DB statements), POST /api/signin (BCrypt dominates). The choice is by request shape and cost, not by measured traffic: the app had no request metrics before plan 14-01. Phase 14.1's dashboards re-rank them from the http_server_requests_seconds_count series this phase creates.

Non-obvious trade-offs:
- A counter registered lazily on its first increment is invisible to increase() for that first event (Prometheus has no prior sample); every counter here is registered at startup, with every tag value of a bounded tag pre-registered.
- ECS JSON applies to local bootRun and test output too; plain-text console logs are gone everywhere. Reversible with one property line.
- If GET /api/signin today reaches the catch-all (HttpRequestMethodNotSupportedException has no arm), every scanner probe is a 500 that pollutes the 5xx ratio; Task 1 tests it first and fixes it only if it reproduces.
- Split note: the Kafka counters, latency buckets and the exact-name scrape test moved to 14-05 so neither plan exceeds the context budget; this plan's counters are still pinned by registry-level tests here and by the scrape test there.
</approaches>

| T-14-18 | Denial of service | Metric cardinality | medium | mitigate | Tags only from fixed sets (move, reason); no path, id or message tags; the per-uri timers use Boot's templated uri, never the raw path |
