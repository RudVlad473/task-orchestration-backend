<objective>
Close the three remaining paging gaps: a CI gate so a broken alert config can never silently stop paging, Flux notifications so a failed or unhealthy production deploy pages even if Prometheus is the thing that broke, and the uptime workflow paging Telegram on failure with a heartbeat against GitHub's silent 60-day schedule disable.

Purpose: D-04 (b), the folded "prod post-deploy health verification" todo, and the guard on D-02/D-15 config.
Output: verify-alerting-config.py with selftest and promtool unit tests in CI, Flux Providers/Alerts with chat ids substituted from a Secret, and a paging uptime workflow.
</objective>

<data_flow>
In CI the gate extracts the Alertmanager config from the HelmRelease and the rule groups from the PrometheusRule and runs the pinned amtool and promtool images over them, including unit tests that replay synthetic series. On the cluster, kustomize-controller emits an error event when a Kustomization fails to apply or its `wait` health check times out; notification-controller matches it against the Alerts and posts it to Telegram with the token from Secret telegram-token. On GitHub, the uptime job probes both public URLs, posts per-environment failures to Telegram, and every run pings healthchecks.io, which pages if the pings stop.
</data_flow>

<approaches>
| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Gate script with pinned amtool/promtool images + promtool unit tests; Flux telegram Providers with postBuild-substituted chat ids; uptime workflow posting to Telegram plus a healthchecks.io heartbeat (research recommendation) | Pro: each path pages independently of the others; config regressions fail CI. Con: one more Flux Kustomization root and one more CI job | Covers the three failure modes the earlier plans leave open |
| B. Flux `alertmanager` provider type (route Flux events into Alertmanager) | Pro: one paging path. Con: Flux events carry no end time and need resolve_timeout tuning; a dead Alertmanager would also silence deploy failures | Rejected (research Finding 6) |
| C. Third-party keepalive action for the 60-day disable | Pro: prevention. Con: gautamkrishnar/keepalive-workflow is blocked on GitHub for ToS reasons | Rejected; heartbeat detection plus a best-effort enable call instead |

Non-obvious trade-offs:
- The Flux Provider's channel must be in spec (Flux Secret keys do not include channel); postBuild substitution keeps the id out of git at the cost of a separate Flux Kustomization `notifications`.
- The keepalive job needs `actions: write`; it is a separate job so the probe job keeps `permissions: {}`. Whether the enable call resets GitHub's inactivity timer is unverified; the heartbeat is the real control.
- Repository secrets, not an environment: environment-bound jobs record a deployment per run (96 a day).
- `wait: true` already makes apps-prod's reconcile fail on an unhealthy rollout; adding healthChecks would be ignored by Flux when wait is on, so the Kustomization is not edited.
</approaches>
