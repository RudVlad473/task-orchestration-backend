<objective>
Schedule the tested backup script as a Flux-managed CronJob, let it reach Postgres, run it once by hand, prove the key cannot read, measure its memory, and rewrite the runbook's "there is no backup" section.

Purpose: closes the production no-backup gap open since the 2026-09-26 cutover (D-01, D-10..D-14), and gives the alerting plan the CronJob identity its missing-backup rule watches (D-15).
Output: CronJob postgres-backup, script ConfigMap, NetworkPolicy peer, optionally the backup image pipeline, a verified first upload, a MEASURED limit and the runbook section.
</objective>

<data_flow>
At 02:17 UTC the CronJob controller creates a Job whose pod mounts the script from a ConfigMap and reads DB credentials and the B2 key from two Secrets by single keys. The pod connects to Postgres through the NetworkPolicy peer that admits only its label, encrypts the dump and uploads it to B2; kube-state-metrics records the Job's success time. The alerting plan turns that timestamp into the missing-backup alert.
</data_flow>

<approaches>
| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Pinned custom image from alpine:3.22 by digest, packages pinned, built by a small workflow, runs as non-root with a read-only root filesystem (research recommendation) | Pro: reproducible, no nightly package download while DB credentials are in the pod, non-root. Con: new workflow, a Docker Hub repo, a manual digest bump | Recommended at Task 1 |
| B. Stock alpine:3.22 by digest plus `apk add` of pinned versions at job start | Pro: no image pipeline. Con: nightly dependency on Alpine mirrors, pinned versions can vanish on a point release, must run as root with a writable root filesystem | Acceptable if the operator prefers no pipeline; the 26h alert and KubeJobFailed catch its failure mode |
| C. A third-party postgres-backup-s3 image | Pro: zero build. Con: unreviewed code holding superuser-adjacent credentials | Rejected |

Non-obvious trade-offs:
- The CronJob is applied by the `data` Flux Kustomization, which also owns the Postgres StatefulSet; a broken CronJob manifest blocks that Kustomization's reconcile, so the render gate runs before push.
- Kustomize's configMapGenerator suffixes the script ConfigMap with a content hash; a script edit changes the CronJob template only, it does not restart Postgres (unlike the init scripts).
- Under Recreate nothing here, but under `concurrencyPolicy: Forbid` a hung run blocks the next night; activeDeadlineSeconds bounds it.
- Option A runs as uid 65534 with readOnlyRootFilesystem, so HOME and WORK_DIR point at the emptyDir (aws-cli writes a cache under HOME).
</approaches>
