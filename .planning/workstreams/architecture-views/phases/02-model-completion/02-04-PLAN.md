## Non-obvious trade-offs
- **Performance:** dynamic views add no check cost beyond the participant and tag rules; the live measurement costs a bootRun of about 25 s plus compose start-up.
- **State invalidation:** steps validate against nothing in the model (research Pitfall 6), so the evidence file is the only tie to the code; a code change can silently stale a step. The line cites make that drift findable, not caught.
- **Security:** the measurement could show that unauthenticated requests create session rows, which would be a finding for the user (unbounded session rows from anonymous traffic). This plan records it, stops at the Task 3 checkpoint, and changes no Java; the fix-app option routes a fix to a separate quick task outside this phase.
- **Shared state:** the measurement uses the repo's local compose Postgres on port 5433, which the user's datastore can also occupy; the task never stops a service it did not start.
</tradeoffs>

Draw the signup, error-status and activity-log scenarios on existing elements (SCEN-01, SCEN-02, SCEN-06), each step tied to a cited line, and settle what the 401 view may claim by measuring it.

Data flow in three sentences: each dynamic view lists steps between leaf participants, and LikeC4 validates only that the participants exist, so the evidence file carries the step-to-code tie. The live measurement sends two cookie-less requests to the app on the host while Postgres logs every statement, and its VERDICT line decides how the 401 view is scoped and worded; a verdict that contradicts ROADMAP criterion 3 stops for the user's decision first. sync.mjs then holds the views to the viewpoint tag and the 5-participant cap.

Output: five scenario views (four if the user defers the 401 view), the evidence file, one measurement record.
</objective>
