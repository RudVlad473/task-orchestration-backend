## Approaches considered (project directive: decided before this PLAN.md)

The 401 "no SQL" claim (research A3, orchestrator question 4):

| Approach | Pros / Cons | Why picked |
|---|---|---|
| A (picked): label the claim authored and measure it once on the app running on the host: Postgres statement log, spring_session row count and Set-Cookie presence, for a JSON client and a default-Accept client | Pro: sees every statement on the wire, Spring Session's included. Con: one-off evidence, not a regression check; needs Docker, ports 5433 and 8080 free, and a bootRun. | The only option that observes the mechanism the claim is about. |
| B: a query-count test through `AbstractAppTest.countQueries` | Con: it reads Hibernate's `getPrepareStatementCount()` (AbstractAppTest.java:304-308), and Spring Session JDBC issues its SQL through JdbcTemplate, which Hibernate statistics never see; the test would pass whether or not a session row is written. Also Java code in a model phase. | Rejected: a test that cannot fail on the claim. |
| C: label authored, no measurement | Pro: free. Con: planning found a concrete way the claim could be false: the main chain uses `SessionCreationPolicy.IF_REQUIRED` with CSRF disabled and no request-cache override (SecurityConfiguration.java:83-128), and Spring Security's default request cache saves an unauthenticated request in a new session unless the client asks for JSON (training knowledge, unverified here). | Rejected as the only step; it is the fallback when A cannot run. |

SCEN-06 composition (research D5):

| Approach | Pros / Cons | Why picked |
|---|---|---|
| A (picked): one view, 5 participants: kanban.api, kanban.publisher, redpanda.activity, kanban.consumer, postgres.table_activity_log; the committed mutation is the first step's title | Pro: one trace, within the cap. Con: the HTTP request is named, not drawn. | Research recommendation. |
| B: two views joined by `navigateTo` | Pro: keeps the client. Con: two views for one trace. | Rejected. |
| C: 6 participants | Con: breaks the participant rule from plan 01. | Rejected. |

Error statuses: one view per outcome (error-401, error-403, error-409), because the standard adopts one dynamic view per outcome and bans branches inside a view (V1); one view with `alt` is rejected. The 400 outcome is not in SCEN-02 and is not drawn.

## Non-obvious trade-offs
- **Performance:** dynamic views add no check cost beyond the participant and tag rules; the live measurement costs a bootRun of about 25 s plus compose start-up.
- **State invalidation:** steps validate against nothing in the model (research Pitfall 6), so the evidence file is the only tie to the code; a code change can silently stale a step. The line cites make that drift findable, not caught.
- **Security:** the measurement could show that unauthenticated requests create session rows, which would be a finding for the user (unbounded session rows from anonymous traffic). This plan records it and does not fix it (Java, out of this phase).
- **Shared state:** the measurement uses the repo's local compose Postgres on port 5433, which the user's datastore can also occupy; the task never stops a service it did not start.
</tradeoffs>

<objective>
Draw the signup, error-status and activity-log scenarios on existing elements (SCEN-01, SCEN-02, SCEN-06), each step tied to a cited line, and settle what the 401 view may claim by measuring it.

Data flow in three sentences: each dynamic view lists steps between leaf participants, and LikeC4 validates only that the participants exist, so the evidence file carries the step-to-code tie. The live measurement sends two cookie-less requests to the app on the host while Postgres logs every statement, and its VERDICT line decides how the 401 view is scoped and worded. sync.mjs then holds the views to the viewpoint tag and the 5-participant cap.

Output: five scenario views, the evidence file, one measurement record.
</objective>
