## Approaches considered (project directive: decided before this PLAN.md)

Anchoring chart-installed components (GATE-01 workloads, PHYS-03):

| Approach | Pros / Cons | Why picked |
|---|---|---|
| A (picked): one element per runtime role, each carrying `workload 'HelmRelease/<name>'`; Prometheus, Grafana and node-exporter share `HelmRelease/kube-prometheus-stack` | Pro: the view shows the scrape topology it exists for; the set-based two-way rule tolerates a shared claim (`sync.mjs:533-536`); placement is already defined for HelmReleases (Phase 1 A8). Con: the check proves the HelmRelease exists and lands in `monitoring`, not that Prometheus runs in it (accepted limit A11). | Research recommendation; every anchor is a document the check reads. |
| B: one element per HelmRelease | Pro: one claim per element. Con: Prometheus, Grafana and node-exporter collapse into one box, so "an edge to each thing they scrape" cannot be drawn. | Rejected: fails criterion 1. |
| C: render the charts (`helm template`) and anchor the real Deployments | Pro: checks what runs. Con: a helm binary and chart downloads inside a one-second check; Phase 1 rejected rendering (ARCHITECTURE N3). | Rejected: cost. |

Where the management port and the backup flow are drawn (PROC-01, research OQ3):

| Approach | Pros / Cons | Why picked |
|---|---|---|

Con: the view grows from 7 to about 13 nodes; its natural width is recorded in plan 05, not judged (no LikeC4 legibility rule exists). | Matches the criterion as written. |
| B: a second `#process` view for backup and Schema Registry | Pro: narrower views. Con: the criterion says "the `process` view"; splitting changes the roadmap, which is the user's call. | Rejected now; available if the user judges the width unreadable. |
| C: the management port only in the Physical view | Con: fails PROC-01. | Rejected. |

Notes (LOGI-01, research D4):

| Approach | Pros / Cons | Why picked |

## Non-obvious trade-offs
- **Performance:** five more workload documents in a set comparison; no measurable change to the check's 1.4 s.
- **State invalidation:** three elements share one HelmRelease claim, so renaming that HelmRelease reports one missing claim, not three; D20 drills the single-claim case (loki).
- **Kafka pair title:** the registry calls (sync) and the Kafka produces (async) merge onto one `kanban -> redpanda` instance pair. Planning measured the merged edge with identical titles: label clean, no kind, LikeC4's default dashed line (research A5 answered). The registry relationships therefore carry the shared title from plan 01, and `process` overrides each label.
- **Security:** monitoring datasource URLs and backup Secret names are in-cluster names; descriptions are written fresh, one sentence each, and the leak gate runs on the model.
</tradeoffs>
