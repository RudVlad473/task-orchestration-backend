Follow-ups on the same running app:
- Burst: 10 further cookie-less `Accept: */*` GETs took the table from 4 to 14 rows (one row per
  request). Statements for the burst were not captured; the row delta is the evidence.
- Lifetime: all 14 rows have principal_name NULL, max_inactive_interval = 10800 s (180 minutes,
  spring.session.timeout=180m, application.properties:174) and were still present, unexpired, about
  3 minutes after the burst (checked 14:47:34Z). Each row has exactly one attribute,
  SPRING_SECURITY_SAVED_REQUEST. So the cookie's Max-Age (600 s) is far shorter than the
  server-side row lifetime (10800 s): anonymous rows outlive the cookie that names them.

Mechanism (read from the Spring Security 6.5.11 sources the app resolves; not from memory):
- SecurityConfiguration.java:87 disables CSRF, :127 sets SessionCreationPolicy.IF_REQUIRED, and no
  requestCache is configured anywhere in src/main/java (`rg -i requestCache src/main/java` finds
  nothing), so the default RequestCacheConfigurer applies.
- ExceptionTranslationFilter.sendStartAuthentication (line 218) calls
  `requestCache.saveRequest(request, response)` BEFORE the authentication entry point runs.
- RequestCacheConfigurer.createDefaultSavedRequestMatcher (lines 144-160) saves a request unless
  it is a favicon, `X-Requested-With: XMLHttpRequest`, or matches application/json,
  multipart/form-data or text/event-stream. Its media-type check ignores MediaType.ALL (lines
  167-168), so `Accept: */*` is NOT treated as JSON and the request is saved. The
  "GET requests only" matcher is added only when CSRF is enabled (lines 148-153); CSRF is disabled
  here, so POST/PUT/DELETE are saved too (request D).
- HttpSessionRequestCache.saveRequest (lines 72-78): `request.getSession().setAttribute(...)`
  with createSessionAllowed = true creates the HTTP session. Spring Session JDBC then persists it
  at commit: INSERT SPRING_SESSION + INSERT SPRING_SESSION_ATTRIBUTES, and the container sends
  Set-Cookie.
- ProblemDetailAuthenticationEntryPoint itself writes no session and no SQL (unchanged from the
  earlier reading); the SQL comes from the request cache that runs before it.

What this means for the error-401 view (not acted on here; orchestrator decides with the user):
the "401 with no SQL step" claim holds for a client that sends Accept containing application/json
(or X-Requested-With: XMLHttpRequest), and is false for a client that sends */*, text/html or no
Accept header, on any method. For that client the view would have to show, between traefik/kanban.api
and the 401, a write to postgres.spring_session (INSERT SPRING_SESSION and INSERT
SPRING_SESSION_ATTRIBUTES, attribute SPRING_SECURITY_SAVED_REQUEST) and the 401 carrying a
Set-Cookie JSESSIONID. It is also a security-relevant finding: anonymous traffic writes one
spring_session row per request, each living 180 minutes.

Not measured / limits: only /api/boards (one protected route) was driven; other protected routes go
through the same filter chain but were not each tried. Behind traefik/production the Accept header a
real client sends is what decides; no proxy was in the path here. The app ran without Kafka. One run,
one machine; not a regression check.
