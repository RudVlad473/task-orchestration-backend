<domain>
## Phase Boundary

Every element, deployment node and view in the published LikeC4 model (`docs/architecture/model/*.c4`) has a description that follows a written wording rule, and the published views are grouped by the Kruchten viewpoint they belong to. The phase opens with an audit that lists each defect with the element it sits on, and a `sync.mjs` rule holds the mechanical part afterwards.

Out of scope: rewriting text that a leak scan would flag (hostnames, Secret names, IPs, key paths). That is Phase 4 criterion 1. This phase writes descriptions that do not add such identifiers, and does not hunt for existing ones.

</domain>

<decisions>
## Implementation Decisions

### Wording rule
- **D-01:** Write a short description-wording rule into `docs/DIAGRAM_CONVENTIONS.md` (section "LikeC4 standard") before the audit, and audit against it. The file has no match for "description" today, so the rule is new text. Proposed content: full sentence, trailing period, a word cap, one fact per sentence, no identifier a leak scan targets. The exact cap is set by the planner from the existing descriptions (currently 6 to 35 words in the part of `model.c4` read). — **Reversibility:** reversible — a doc edit.

### Completeness
- **D-02:** Elements, deployment nodes and views must have a description. Relationships keep their label as their only text; the existing "protocol-level fact" label rule in `DIAGRAM_CONVENTIONS.md` stays the rule for them. Generated elements (`generated.c4`, which has no `description` lines) are covered by the audit too: the audit decides whether the generator or an authored overlay supplies the text, and reports it rather than assuming.

### Grouping
- **D-03:** The published views are grouped by the Kruchten viewpoint they relate to: logical, process, development, physical, scenarios, with `index` outside the set. Today `views.c4` interleaves them (index, process, data, development, production, delivery, then the scenarios; the `monitoring` view is not in that file's first 140 lines of declarations I read, so the planner must locate it). The grouping must show in the built site's navigation, not only in file order. Which LikeC4 construct does that (view groups, title paths, or ordering by tag) is for the researcher to settle against the LikeC4 docs at the pinned version. — **Reversibility:** reversible — view declarations only; ids stay, so `/view/<id>/` URLs do not change unless the construct renames them. The planner must check that.
- **D-04:** Property order inside element blocks (`technology`, `description`, `metadata`) is left to the planner; the user stated a preference only for Kruchten grouping of views.

### Enforcement
- **D-05:** Add a rule to `docs/architecture/sync.mjs` (`check` mode) for the mechanical part of D-01 and D-02: description present on every element, deployment node and view, and the trailing period. The rule needs a drill row in `drills.tsv`, a regenerated `drill-output.txt` and a hook self-test case, per the 03-08 notes in STATE.md. Wording that no script can judge (clarity, one fact per sentence) stays with the audit. This supersedes the 03-08 "no gate reads prose" position for presence and punctuation only.
- **D-06:** The grouping in D-03 is checked by the existing view-membership and viewpoint-tag checks where they already cover it; a new check is added only if the researcher finds the chosen LikeC4 construct can silently drop a view from its group.

### Claude's Discretion
- Word cap, property order, the file layout of the audit report, and which LikeC4 construct implements the grouping.

</decisions>
