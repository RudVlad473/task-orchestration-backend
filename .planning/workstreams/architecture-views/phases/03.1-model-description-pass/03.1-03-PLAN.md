<tradeoffs>
## Approaches considered (project directive)

Where presence and punctuation are enforced (D-05):

| Approach | Pros / Cons | Why picked |
|---|---|---|
| Picked: one `checkDescriptions` function in `sync.mjs check` over `computed.elements()`, `computed.deployment.nodes()` and `computed.views()`, reading `description.text` | Pro: the honesty-gate pipeline already runs in the hook and in CI (`likec4-model-drift`). The findings name the item's id, so drill output names the element. Prototyped in research, red and green. Con: three helpers and two self-test cases that inject undescribed elements must change in the same commit. | Smallest place, and it reuses the drill and self-test machinery. |
| A LikeC4-side constraint (spec or validation) | Con: LikeC4 1.60.0 has no required-property declaration. V2 already showed the DSL cannot even declare metadata keys. | Impossible. |
| A separate lint script | Pro: decoupled. Con: a new entry point in the hook and CI, a new self-test, and the same computed-model load done twice. | Rejected: duplicate wiring. |

Generated text (D-02): the template states provenance only, `sync.mjs draws this table from the Flyway migration <file>.` and `sync.mjs draws this package from its source folder and import lines.` See 03.1-01-PLAN.md for the template-versus-map matrix.

Label-only relationships (D-02) are held by a verify gate in Task 2, not by a sync.mjs rule. D-05 limits the script to presence and the trailing period on elements, deployment nodes and views, and this phase does not widen it.
- The gate reads `description` from every computed relationship, which falls back to `summary`, and fails on any that is non-empty.
- It runs at phase end, after every task that writes model text, so a description added inside a relationship block anywhere in the phase is caught before the phase closes. The model invariance gate cannot catch it, because it lets description lines through.
- Measured at planning time: 0 on the real model, and 1, naming `client -> traefik`, on a scratch copy with a description in that relationship's block.
- After the phase nothing holds it. Making it permanent would mean extending D-05, which is the user's call.

The "not caught before" record: the BASE script is run against the final model, with generated.c4 re-rendered by that same script. The old script renders no descriptions, so against the committed generated.c4 it would report "generated.c4 is stale" on every drill. That would make every drill red for a reason unrelated to the rule.

## Non-obvious trade-offs

- **Layout:** 20 generated nodes gain an 11 or 9 word line of text. Research measured +72 px on `data` and +132 px on `development` for an 11-word line. The dated size tables are not re-measured, and the SUMMARY says so.
- **Tampering surface:** the template interpolates only the migration file's base name. That name is already written into `metadata source` and is read by `readdirSync` filtered to `.sql`. A quote in it would break the .c4 parse and be reported as `model does not validate`, exactly as today. Package text interpolates nothing.
- **Coupling:** D28 to D29b anchor on block heads and description lines by range, so a later rewording of the index, b2, github.runner or grafana text does not break them. Self-test case 17 anchors on the index description verbatim, so a reword of that line must update the case.
- **Performance:** the rule visits 99 items once, which is negligible. The harness (about 60 s) runs three times in this plan and the self-test (about 60 s) twice. Estimate check (`gsd_run query estimate-check --tokens 85000 --calibrated`, 2026-10-29): budget 100000, ratio 0.85, not over budget, calibration factor 1 from 0 samples, confidence low.
</tradeoffs>

<objective>
Make `sync.mjs check` hold the mechanical half of the wording rule (D-05). Have the generator supply the generated elements' text (D-02). Record the new rules' drills not caught before and caught after (D-05, D-06), and state both rules in the standard.

Data flow in three sentences: `generate` now writes a description line into each table and package block of generated.c4, and `check` still compares that file byte for byte with a fresh render. checkDescriptions walks the computed elements, deployment nodes and views and reports each one whose description text is empty or lacks a final period. The drill harness edits scratch copies, so each new row is shown caught by this script and not caught by the BASE script.

Output: the rule and the template in sync.mjs, regenerated generated.c4, six drill rows with fixed helpers, two new self-test cases, the regenerated drill record, the before-record, and the standard updated.
</objective>
