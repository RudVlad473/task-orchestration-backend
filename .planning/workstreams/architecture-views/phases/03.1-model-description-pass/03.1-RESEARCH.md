## Summary

The grouping question is settled by running it. At the pinned LikeC4 1.60.0, a `views '<label>' { ... }` block (or a `/` in a view title) places its views in a folder, and the built site renders folders in its navigation panel. Folders sort **alphabetically**, so plain names give Development, Logical, Physical, Process, Scenarios, which is not the Kruchten order. Numeric prefixes (`1 Logical` ... `5 Scenarios`) give the Kruchten order, and `index` sits at the root below the folders. No view id changes, `/view/<id>/` still resolves, PNG export names are still flat by id, and the existing `sync.mjs check` passes unchanged on the regrouped model. A view moved into an unlabelled `views { }` block silently leaves its group and the current check still exits 0, so D-06's condition is met: a folder check is needed (about 8 lines, prototyped and proven red and green).

The description inventory is smaller than CONTEXT feared. All 42 hand-written elements and all 21 views already have a description. The gaps are 20 generated elements (6 tables, 14 packages), 13 of 16 deployment nodes (8 namespaces, 5 providers) and 9 descriptions with no trailing period (8 elements, 1 node). `extend` cannot carry a `description` at 1.60.0 (parse error, run), so an "authored overlay" on generated elements is impossible; the text must come from the generator. A generator-side template is the only option that keeps hook self-test `test_06` (adds a table, regenerates, expects pass) green without a hand-written map entry per new table.

The `sync.mjs` rule is a 15-line function over `computed.elements()`, `computed.deployment.nodes()` and `computed.views()` reading `item.description.text`. Adding it also forces three companion edits that the 03-08 notes did not list: the drill helpers `certmgr_into` and `lonely_into` and the self-test cases `test_07` and `test_08` inject elements with no description and go red (observed for the two drill helpers); and the D9 block of `drill-output.txt` gains one folder line.

**Primary recommendation:** Group with numbered `views 'N Viewpoint' { }` blocks plus `order N` for intra-folder order; supply generated descriptions from a generator template; add `checkDescriptions` and `checkViewFolders` to `check()`; keep both new rules' drills, helper fixes, self-test cases and `drill-output.txt` regeneration in the same plan as the rule.

### Q1. Which LikeC4 construct groups views in the built site's navigation

**Answer: `views '<folder label>' { ... }` blocks, with numbered labels. [VERIFIED: run at likec4 1.60.0]**

Evidence, in order:

1. **Version.** `docs/architecture/package.json` pins `"likec4": "1.60.0"`; `docs/architecture/node_modules/likec4/package.json` reads `"version": "1.60.0"`; the lockfile resolves `likec4@1.60.0`. [VERIFIED: files read]
2. **Documented constructs.** LikeC4 docs "Organize views": a `/` in a view title makes a folder (`'Deployment / Production'`); `views 'Domain 1 / Subdomain' { ... }` puts every view in the block under that folder; `\/` escapes a literal slash; views in one folder take `order <non-negative int>`; "Folders are still sorted alphabetically"; the page lists no other sort option. [CITED: https://likec4.dev/dsl/views/organize/ ; same text via context7 `/likec4/likec4`, source `apps/docs/src/content/docs/dsl/Views/organize.mdx`] The docs bundled in the pinned package confirm folders exist at 1.60.0: "escape `\/` to include a literal `/` without it being read as a view-folder separator" and "Organize views -> views "Use Cases" { ... } (folder label)". [VERIFIED: `node_modules/likec4/skills/likec4-dsl/SKILL.md` lines 15 and 356]
3. **Not constructs for this.** The DSL `group { include ... }` inside a view draws a box around elements in a diagram; it is not navigation. [CITED: context7, `Views/predicates.mdx`] LikeC4 has no tag-driven navigation order: the organize page names only folders, `order` and alphabetical folder sort. [CITED: likec4.dev organize page] The bundled configuration reference documents no navigation option (its only navigation-related setting is `implicitViews`). [VERIFIED: `skills/likec4-dsl/references/configuration.md` grep for navigat/sidebar/folder/order returned only line 104, `implicitViews`]
4. **Experiment A (plain labels).** On a scratch copy of the model inside this phase dir I split `views.c4` into per-viewpoint `views 'Process' { }`, `'Logical'`, `'Development'`, `'Physical'`, `'Scenarios'` blocks, and relabelled the `views` heads in `monitoring.c4` and the two `scenarios-*.c4` files. The computed model's `rootViewFolder` tree printed: folders `Development, Logical, Physical, Process, Scenarios` (alphabetical), then the `index` view at the root; `errors: []`.
5. **Experiment B (numbered labels, `order`).** With labels `1 Logical`, `2 Process`, `3 Development`, `4 Physical`, `5 Scenarios` the folders sort in Kruchten order. `likec4 build -o <scratch> <scratch model>` built (3.5 s), the page at `/view/data/` loaded under a history-fallback server, and its breadcrumb read `1 Logical > Logical view: tables and the foreign keys that own them`. Clicking the breadcrumb opened the navigation panel (screenshot read): folders `1 Logical`, `2 Process`, `3 Development`, `4 Physical`, `5 Scenarios`, then `System context` (the `index` view) below them. [VERIFIED: shot-scraper against the built scratch site]
6. **`order`.** Inside the Physical folder the file-merge order was `monitoring, production, delivery` (file names alphabetical: `monitoring.c4` before `views.c4`). Adding `order 1`/`2`/`3` to `production`/`delivery`/`monitoring` gave `production, delivery, monitoring`. **`order N` must come after the view's `#tag` line**: placed before it, the parse fails with `Expecting token of type '}' but found '#'`, three views lost their body (title became the bare id, tags empty) and `likec4.getErrors()` reported it. [VERIFIED: run]

**Does any option change ids or URLs?** No, for the recommended construct. After Experiment B the ids printed by the model were unchanged (`index development data ... signin-ceiling`, 21 ids), `/view/data/` resolved, and `likec4 export png --seq` wrote 21 files flat by id (`png-b/data.png`, not `png-b/1 Logical/data.png`). [VERIFIED: run] The title-path variant (`title '1 Logical / ...'`) also keeps ids, but changes every displayed title and needs `\/` escapes; it was not built (see matrix).

**Can it silently drop a view from its group (D-06)? Yes. [VERIFIED: run]** I changed one block head in the Experiment B copy (`views '5 Scenarios' {` to `views {`, which puts `signin-ok`, `signin-bad-credentials`, `signin-ceiling` in the root folder). `node docs/architecture/sync.mjs check --model <copy>` printed `OK (62 elements, ...)` and exited 0; the probe showed the three views at the root. The view-membership rule (instances in deployment views) and the viewpoint-tag rule (tags) never look at folders. A mistyped label would create a sixth folder the same way, and a `#physical` view inside `views '1 Logical'` passes by the same mechanism (by construction, not run). So D-06 licenses one new check. It is prototyped under Code Examples and proven: 20 findings on the current model (every non-index view sits at the root today), 0 on the regrouped model, 3 on the model with the block head removed.

**Side finding:** descriptions are visible in the navigation panel (each view row shows a one-line truncated description) and element descriptions render as small text inside diagram nodes (screenshot of `data`: the `spring_session` and `activity_log` nodes show their text). ### Q3. Does `generated.c4` get its elements from a generator in `sync.mjs`

Yes. `render()` (line 537) composes `renderTables()` (495-506), `renderForeignKeys()` (508-514), `renderPackages()` (516-527) and `renderPackageEdges()` (529-535). `check()` recomputes `render()` and compares it byte for byte with the file (`if (want !== have) problems.push('generated.c4 is stale: ...')`, line 572). [VERIFIED: sync.mjs read] The element blocks it writes today are:

```
    table_users = table 'users' {
      #generated
      metadata { source 'src/main/resources/db/migration/V1__init.sql' }
    }
```
and the same shape for `pkg_<name> = component '<name>'` with `source '<APP_PACKAGE_DIR>/<name>'`. No `description`.

**What can supply descriptions?**
- **An authored overlay cannot.** `extend postgres.table_users { description '...' }` fails: `Expecting token of type '}' but found 'description'` (run on a scratch copy). `extend` accepts children and metadata, not a description. [VERIFIED: run] Editing `generated.c4` by hand is refused by the header (`// GENERATED ... Do not edit.`) and by the stale check.
- **The generator must emit it.** Two shapes: (a) a template over facts the generator already reads (table name, migration file; package name), or (b) a map in `sync.mjs` of authored text per table and package.
- **Recommendation: (a).** `test_06_migration_with_regenerated_model_passes_the_check` in the hook self-test adds `CREATE TABLE selftest_drift` (`MIGRATION_SQL`, self-test line 45), runs `generate`, and expects the commit to pass. With (b) the new table has no map entry, so the new description rule fails and `test_06` goes red; with (a) the generator writes the description itself and `test_06` stays green. (a) also keeps the DIAGRAM_CONVENTIONS ladder honest ("`generated`: written from code, never edited"): the text states only what the generator read. Example shape, to be fixed by the planner: `description 'Table users, created in V1__init.sql.'` and `description 'Top-level package service under the application root package.'`. No `COMMENT ON` exists in the migrations and no `package-info.java` exists, so there is no in-code prose to read (`rg -i "comment on"` over `db/migration` and `rg --files -g package-info.java` over `src/main/java` both returned nothing). [VERIFIED: rg]
- Cost of (a): the generated text is generic. If the user wants domain text on tables (for example "the table that holds the account and its password hash"), that is (b) plus a decision that `test_06` and drill D1 get a map entry. That is a choice for the planner and user, surfaced as Open Question 1.

### Pattern 1: Viewpoint folder by block label (recommended)
**What:** one `views '<N Viewpoint>' { }` block per viewpoint; blocks of the same label merge across files.
**When to use:** whenever a view belongs to a Kruchten viewpoint (all but `index`).
**Example (run at 1.60.0):**
```likec4
views '4 Physical' {
  deployment view production {
    #physical
    order 1
    title 'Physical view: what runs where'
    ...
  }
}
```
`order` goes after the `#tag` line. Folder labels are the contract with `checkViewFolders`; they must not change without changing `VIEW_FOLDERS`.

### Pattern 2: A rule is a function over the computed model
Follow `checkEdgeLabels`: `(computed, problems)`, iterate in sorted id order, push one string per finding, state each finding with the item's id so the drill output shows the element it sits on (this is also what the audit's "each defect with the element it sits on" asks for).

### Anti-Patterns to Avoid
- **Authoring descriptions on generated elements by editing `generated.c4`** or by `extend`: the first is overwritten and flagged stale, the second does not parse.
- **Folder labels without numbers**: the navigation then reads Development, Logical, Physical, Process, Scenarios.
- **Putting `order` before the tag**: a parse error that blanks the view (caught only by `model does not validate`).
- **Counting a deployment instance as a description gap**: instances inherit the element's description.
- **Folder rule that also fires on a view with 0 or 2 tags**: the tag rule already reports those; skipping them keeps D6 and D6b output unchanged (a first prototype without the guard printed `expected 'undefined'`).

## Trade-off Matrices (inputs for the PLAN.md the project CLAUDE.md requires)

**Grouping construct**

| Approach | Pros/Cons | Why Picked |
|----------|-----------|------------|
| `views 'N Name' { }` block labels | Pros: titles untouched, edits are block heads, ids and URLs unchanged, merges across files. Cons: alphabetical folder sort forces numeric prefixes; a misplaced block silently regroups | Picked: smallest edit, verified end to end; the silent-regroup risk is closed by `checkViewFolders` |
| `title 'N Name / Title'` paths | Pros: folder visible in the title line itself. Cons: edits 20 titles, needs `\/` where a title holds a slash, titles in other docs change | Not picked: larger blast radius for the same result |
| Plain labels, accept alphabetical | Pros: no numeric noise. Cons: wrong Kruchten order (verified) | Not picked: the user asked for Kruchten grouping |

**Generated-element descriptions**

| Approach | Pros/Cons | Why Picked |
|----------|-----------|------------|
| Generator template from facts it reads | Pros: no upkeep, `test_06` and drill D1/D8 unaffected, stays on the `generated` rung. Cons: generic text | Picked |
| Authored map in `sync.mjs` | Pros: domain text. Cons: new table needs a map entry, so `test_06` goes red and the rule blocks a legitimate migration; text unchecked | Not picked unless the user wants domain text (Open Question 1) |
| Overlay via `extend` | Does not parse at 1.60.0 | Impossible |

Non-obvious trade-offs: description text renders inside diagram nodes, so longer text widens layouts (measured +72 px on `data`, +132 px on `development` for an 11-word line on every generated element); descriptions publish on the staging-certificate site on the next push, and Phase 4 scans them, so new text must add no hostname, Secret name, IP or key path (security below).

## Common Pitfalls

### Pitfall 1: A silently regrouped view
**What goes wrong:** a view in an unlabelled block, or under a mistyped label, leaves its folder; `check` stays green. **Why:** no existing rule reads folders. **Avoid:** `checkViewFolders` with the drill below. **Warning sign:** the navigation panel shows a view at the root next to `System context`.

### Pitfall 2: `order` before the tag line
**What goes wrong:** parse error, view body dropped. **Avoid:** tag first, then `order`. Caught by `model does not validate`.

### Pitfall 3: Injected test elements without descriptions
**What goes wrong:** the new rule turns the controls D13b/D16b and self-test `test_07`/`test_08` red for a reason unrelated to what they prove. **Avoid:** add descriptions to `certmgr_into`, `lonely_into` and the two self-test model snippets in the same plan as the rule.

### Pitfall 4: Rewriting `drill-output.txt` by hand
**What goes wrong:** a stale or hand-edited record. **Avoid:** regenerate with `fish docs/architecture/drill.fish > docs/architecture/drill-output.txt` after the model is clean, and read the diff: the expected deltas are the new rows and the D9 line, and nothing else (`diff` against the committed file).

### Pitfall 5: Red record against the wrong baseline
**What goes wrong:** claiming a drill "not caught before" without running the old script. **Avoid:** run the harness with `SYNC=<old sync.mjs>` (from `git show <pre-rule-commit>:docs/architecture/sync.mjs`) in a scratch location and keep the output as a phase artifact like `02-drills-before.txt`. Because the old script ignores descriptions and folders, MODEL can stay the new model.

### Pitfall 6: Word counts that cannot be re-run
**What goes wrong:** the cap decision rests on a count nobody can reproduce. **Avoid:** the audit step stores the inventory script and its TSV in the phase dir.

### Pitfall 7: New description text that a leak scan flags
Phase 4 scans for hostnames, Secret names, IPs, key paths. Existing descriptions already cite repo paths (`infra/vm/k3s/install.sh`, `k8s/...`) and `KANBAN-INGRESS`; this phase must not add more and need not remove them (Phase Boundary). A generator template that names a migration file path adds a repo-relative path already present in `metadata source`.

### `checkDescriptions` and `checkViewFolders` (prototype run; both green and red)
```js
// Source: prototype written and run this session against docs/architecture/model;
// reads RichTextOrEmpty (@likec4/core types/RichText.d.ts: `text: string` when nonEmpty, `null` when empty).
function checkDescriptions(computed, problems) {
  const surfaces = [
    ['element', [...computed.elements()]],
    ['deployment node', [...computed.deployment.nodes()]],
    ['view', [...computed.views()]],
  ]
  for (const [surface, items] of surfaces) {
    for (const item of items.sort((a, b) => a.id.localeCompare(b.id))) {
      const text = item.description.text
      if (!text) problems.push(`${surface} ${item.id} has no description`)
      else if (!text.trimEnd().endsWith('.')) problems.push(`${surface} ${item.id} description does not end with a period`)
    }
  }
}

const VIEW_FOLDERS = { logical: '1 Logical', process: '2 Process', development: '3 Development', physical: '4 Physical', scenarios: '5 Scenarios' }

function checkViewFolders(computed, problems) {
  for (const view of [...computed.views()].sort((a, b) => a.id.localeCompare(b.id))) {
    const own = [...view.tags].filter((t) => VIEWPOINTS.includes(t))
    const want = view.id === 'index' ? '' : VIEW_FOLDERS[own[0]]
    if ((own.length === 1 || view.id === 'index') && view.folder.path !== want) {
      problems.push(`view ${view.id} is in folder '${view.folder.path}', expected '${want}'`)
    }
  }
}
```
Results of the prototype: real model, unmodified: 33 `has no description`, 9 `does not end with a period`, 20 `is in folder` (every non-index view is at the root today). Regrouped model: 33, 9, 0. Regrouped model with the three signin views moved to an unlabelled block: 3 `is in folder` findings naming them. `VIEW_FOLDERS` duplicates the folder labels in the `.c4` files, the same way `VIEWPOINTS` duplicates the tags in `spec.c4` (line 47 of sync.mjs says so); keep the comment honest the same way. `view.folder.path` is `''` and `view.folder.isRoot` is true for a root view. [VERIFIED: probe output] `item.description.text` is `null` for an empty or missing description, so `''` also fails the rule. The `ancestors` and instance iterators are not needed.
