## Approaches considered (project directive)

How views are grouped in the site's navigation (D-03, construct left to research):

| Approach | Pros / Cons | Why picked |
|---|---|---|
| Picked: one `views '<N Viewpoint>' { }` block per viewpoint, labels `1 Logical` to `5 Scenarios`, `order N` inside the Physical and Scenarios folders | Pro: titles untouched, ids and URLs unchanged, blocks merge across files, built and viewed at 1.60.0 (research Q1). Con: the numbers show in the navigation. A misplaced block silently regroups a view. | Smallest edit. The silent-regroup risk is closed by checkViewFolders (D-06). |
| `title 'N Viewpoint / Title'` paths | Pro: the folder also shows in the title. Con: edits all 20 titles and needs `\/` escapes. Titles quoted in other docs change. | Rejected: larger blast radius for the same navigation. |
| Plain labels (`Logical` ... `Scenarios`) | Pro: no numbers. Con: folders sort alphabetically, so Development, Logical, Physical, Process, Scenarios (verified). | Rejected: not Kruchten's order. |

Order inside a folder (Claude's discretion): only the multi-view folders get `order`. Physical reads production, delivery, monitoring. Scenarios reads the auth flows first (signup-ok, then the three signin views), then the error statuses, the activity log, delivery, edge and backup. Without `order`, monitoring.c4 sorts first and the signin views last, because files merge alphabetically (measured).

## Non-obvious trade-offs

- **State invalidation:** VIEW_FOLDERS repeats the folder labels, as VIEWPOINTS repeats the tags in spec.c4. Renaming a label means editing both, and check fails until they agree.
- **Parse hazard:** an `order` line placed before the viewpoint tag fails to parse and blanks the view. Only `model does not validate` reports it (research Pitfall 2). Every `order` line goes directly after the tag line, and a probe with this exact layout parsed with 0 errors.
- **Drill and self-test anchors:** D6, D6b, D9 and D18, and self-test cases 12 and 15, match view lines by text with a four-space indent. Each view's own lines stay byte-identical. The harness gate proves the only drill change is D9's new folder line.
- **Deployment nodes moved here (checker revision, scope_sanity):** the node descriptions and the two drill-anchor edits came from plan 01, which now stays within 10 files. They stay one task and one commit:
  - LikeC4 refuses a description after an `instanceOf`, so with namespace descriptions in place the old anchors fail D11, D16 and D16b (measured while planning).
  - The reworked anchors insert after the description line. Before that line exists they would put certmgr outside the empty flux-system and cert-manager blocks, because sed's `n` steps onto the closing brace. That is read from the sed program; it was not run.
  Neither half can land alone.
- **Every node-header anchor, measured (checker revision 2):**
  - The anchors in `drills.tsv` and `drill.fish` that touch a deployment-node header are D10 (deletes the cert-manager block), D11's second row, D12b's first row (inserts `metadata { nodekey 'x' }` after the kube-system header) and `certmgr_into`. No anchor touches a provider header.
  - On 2026-10-29 the full 39-drill harness ran on a scratch copy in the phase directory, since deleted. In that copy, all 8 namespace and all 5 provider blocks opened with a description line.
  - With today's anchors, the output differed from drill-output.txt only in D11, D16 and D16b. Each failed with "model does not validate: Expecting token of type '}' but found `description`". D10 and D12b reproduced exactly, so LikeC4 accepts a `metadata` block before the description.
  - With the reworked D11 row and `certmgr_into` from Task 3, the whole output was byte-identical to drill-output.txt.
  - So D12b needs no change, and no file beyond Task 3's five is needed.
- **File count:** this plan lists 10 files, at the limit. Every one is edited by a task: the four view files and sync.mjs (Tasks 1 and 2), and deployment.c4, edge.c4, delivery.c4, drills.tsv and drill.fish (Task 3). The measurement above shows the two drill files are required.
  - The cheapest margin would move the five provider-node rows (edge.c4, delivery.c4) into plan 01 Task 2. That splits the deployment-node audit-text gate across two plans and needs a per-id variant of it, which costs more than a one-file margin buys. Left at 10.
- **Performance:** the rule visits 21 views once, which is negligible beside the model load (about 1 s). The harness runs twice (Tasks 1 and 3, about 60 s each) and the self-test once. Estimate check (`gsd_run query estimate-check --tokens 85000 --calibrated`, 2026-10-29): budget 100000, ratio 0.85, not over budget, calibration factor 1 from 0 samples, confidence low.

<objective>
Group the published views by Kruchten viewpoint in the site navigation (D-03), and hold the grouping with a folder rule (D-06). Bring every view and deployment-node description to the wording rule (D-01, D-02), with the two drill anchors the node descriptions need.

Data flow in three sentences: LikeC4 puts every view declared inside `views '<label>' { }` into the folder of that label. `likec4 build` writes those folders into the site's navigation, and `order N` sets a view's place inside its folder. checkViewFolders reads each computed view's `folder.path` and its viewpoint tag, and reports a view whose folder is not the one VIEW_FOLDERS assigns to that tag.

Output: regrouped views in four model files, the folder rule in sync.mjs, view and deployment-node descriptions equal to the audit, and the D11 row and certmgr_into helper reworked.
</objective>
