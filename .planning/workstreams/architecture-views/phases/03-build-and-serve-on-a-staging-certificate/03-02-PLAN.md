## Non-obvious trade-offs
- **Pipeline and production cost:** the first push carries the whole unpushed backlog, including quick task 261028-m6k's change to SecurityConfiguration.java and its test. That starts deploy.yml: tests, two image pushes and Flux rolling the app in kanban-prod and kanban-nonprod. This is why Q1 is a blocking-human decision and not a default.
- **Tags:** `github.run_number` counts pull-request, dispatch and failed runs too, so tags skip numbers; the numerical ImagePolicy only needs them monotonic.
- **Push range:** `git push origin <sha>:refs/heads/main` sends every ancestor origin lacks, and each plan leaves record, summary and state commits behind it. So the push procedure classifies every commit in the range, every authorizing question (Q1, Q2, Q5, Q6, Q4 option 2) names the planning-only commits its push carries, and a push that must carry exactly one commit is preceded by the flush, which pushes those commits first. Alternatives weighed: pushing the records with each one-commit push (the range is then no longer one commit, so the model-only clause would not be literal) and cherry-picking the one commit onto origin/main on a side branch (new SHAs, and local main diverges from what was pushed).
- **Security:** the drift pull request runs main's unchanged workflow text with the repository's default read token and no environment; only the publish job, which the pull request skips, names an environment. That holds for this pull request because it does not edit the workflow; for a branch that does, only Q7's branch policy refuses the environment, and the probe in Task 3 is that case.
- **Q7 numbering:** Q5 and Q6 are plan 06's questions, already named in plans 06 and 07, so the new question here is Q7; plan 06's gates match `Q[56]` and this plan's match `Q[1-47]`, so neither counts the other's lines.
- **Recorded assumptions:** A5 (the namespace's default privacy for a repository created by `docker push` is unknown) is avoided by creating the repository by hand, public, before the push; whether DOCKERHUB_TOKEN may create a repository is not tested. A1 (download-artifact v4 pairs with upload-artifact v4) is settled by the first run.
</tradeoffs>

Push procedure (this plan defines it; plans 03, 06 and 07 use it verbatim):

3. Write into the plan's record `git rev-list --count origin/main..HEAD`, `git log --oneline origin/main..HEAD` (for more than 20 commits, the count, the first and last five lines and the path classes from step 4 instead), and `git diff --name-only origin/main HEAD` reduced to top-level directories with counts.
4. A push by SHA sends every commit origin lacks, so classify every commit `git log --format=%h origin/main..HEAD` lists, and write the classes into the record: (a) the commits the authorizing DECISION names; (b) planning-only commits, every changed path under `.planning/` (records, decisions, summaries, state; `git diff-tree --no-commit-id --name-only -r <sha>` per commit), which every authorizing question names explicitly as part of its push; (c) the step 2 merge. 5. `PUSH_SHA=$(git rev-parse HEAD)`, then `git push origin "$PUSH_SHA:refs/heads/main"` (SESSION_LESSONS lesson 8: an explicit SHA, never a branch name, never `--force`). Record `PUSHED <sha>`.

Any other commit: stop and report; that one-commit push is then not made. Nothing to push: record `FLUSHED nothing to push`.
