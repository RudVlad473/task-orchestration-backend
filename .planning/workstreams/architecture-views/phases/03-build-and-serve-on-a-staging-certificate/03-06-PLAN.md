## Non-obvious trade-offs
- **Latency:** the Flux source polls every minute and the image scan and automation every five, so push to first rollout and new tag to rollout are each a few minutes; about 12 minutes total is arithmetic (research A6), and this plan records the real figures.
- **Rate limits:** the Certificate is on the staging issuer, so retries cost nothing at Let's Encrypt; the production issuer's limit (5 per exact name per 7 days) matters only for the Phase 4 flip.
- **Edge memory:** Traefik runs at 64Mi with 2 restarts before this phase; Task 3 compares its restart count around 10 concurrent cold loads of the site (research open question 4), read-only.
- **CT logs:** whether staging certificates reach public CT logs is assumed not (research A3); Task 3 records what crt.sh returns for the name and writes no claim into the docs either way.
- **Red before green on the live host:** before the push, Traefik answers the architecture host with its default certificate and a 404, so the issuer, `/`, and deep-link probes are each run once then (BASELINE) and fail; the after-lines are their green halves. Two clauses get no live failing case, and plan 07's gate says so: the other hosts' checks are a regression control against their own baseline (a failing case would mean breaking a live host), and `/@fs` cannot be pointed at a dev server on the cluster, so its failing case is plan 01's local dev-server control. Alternatives weighed: a scratch IngressRoute with a deliberately wrong backend (a cluster write for a probe, and it would share the hostname's routing with the real one) and no baseline at all (every live line would be an after-state only).
- **Push range:** the push carries every unpushed commit, so Q5 names them by class (plan 04's site commit, plan 05's two drills commits, the decisions commit, planning-only commits, a Flux merge), and the push procedure's step 4 classifies each one in the record before pushing.
</tradeoffs>

<objective>
With the user's authorization, probe the architecture host once before anything changes, push the site's commit and observe Flux serve the static build at the architecture hostname over HTTPS on a staging certificate, then confirm from outside that only static output is reachable, deep links render and the missing-asset response is what the measurement promised.

Data flow in three sentences: the push makes Flux create the namespace's objects and cert-manager solve an HTTP-01 challenge through a ClusterIP solver Service to issue architecture-tls from the staging issuer, after which Traefik terminates TLS for the host and forwards to nginx on 8080. The same push changed the model, so architecture-site.yml publishes a new tag, Flux's ImagePolicy picks it, the automation commits the bump into the overlay, and the pod rolls; that bump commit starts no site run. Every observation is a read-only SSH or HTTP call, recorded line by line in 03-06-live.txt.

Output: the decision lines and the live record.
</objective>
