## Non-obvious trade-offs
- **Performance:** a full replay copies the k8s tree and the model into a scratch directory and runs `sync.mjs check` once per drill (36 drills before this plan); each task replays twice (once to write drill-output.txt, once in verify with `cmp`). No timing is assumed; the Bash timeout is the default 600000 ms.
- **Security:** run_drills hands the value field to `sed -i --sandbox -e` as one argument from a variable, on `$scratch/<file>` only (no eval, the kind switch is an allowlist, and `--sandbox` refuses the `e`, `r` and `w` commands); the real model and manifests are never edited, and each task checks `git status` on k8s and the model after its replay.
- **State invalidation:** drill-output.txt's DRIFT header carries element and workload counts that plan 04 changed; the comparison reads only `== ` and `exit=` lines, so changed counts are expected and a changed exit code is not.
- **Concurrency:** another session moving the drill harness again is the realistic failure here, not a broken drill (s6i's own mutation check rewrote drills.tsv for about 85 s before restoring it from git); the state detection reads `git status` on drill.fish, drills.tsv, the deleted sed-drills.tsv path and drill-output.txt and stops rather than editing over it (SESSION_LESSONS lesson 2), and each commit names its two paths with `git commit -- <paths>`.
- **D25's address:** `0,/re/` is a GNU sed address that renames only the first `  name: architecture-site` line, the Deployment's (it precedes the Service in the file); the Service keeps its name, so the drill moves one fact.
</tradeoffs>
