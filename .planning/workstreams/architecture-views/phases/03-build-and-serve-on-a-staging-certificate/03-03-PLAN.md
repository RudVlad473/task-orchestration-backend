## Non-obvious trade-offs
- **Memory:** a rung fails on a restart, an OOM termination, an OOM line in dmesg or a pod that never turns Ready. Page cache is not an OOM signal here (the runbook's anon plus shmem finding), so anon and shmem are recorded and file pages are not judged. The adoption rule copies Traefik's row: request at the lowest passing rung, limit at twice it.
- **Node pressure:** each rung's pod requests at most 64Mi on a node with about 7.9 GiB; the 10 concurrent cold loads are driven from the VPS host straight to the pod IP and never pass Traefik, so no public route or live pod is involved.
- **State invalidation:** the cert-manager FAQ's re-issue triggers do not include an issuer edit, so the live Certificates should not re-issue (research A2, an inference); the before and after snapshot of revision and notAfter turns it into an observation. If they did re-issue, they would do it on the production issuer, so the snapshot is read within minutes of Flux applying the edit.
- **Security:** the solver Service type changes nothing about who can reach the challenge; Traefik's Ingress provider routes to a ClusterIP Service the same way (research A4, confirmed when the site's staging Certificate turns Ready in plan 06).
</tradeoffs>

<objective>
Measure the site image's memory floor on the VPS and adopt a limit from it, and, when the user chose it, switch both ClusterIssuers to a ClusterIP solver Service in its own commit and push it, with no other k8s or app change in the push, before the site's Certificate exists.

Data flow in three sentences: a scratch pod runs the published tag under each rung's limit while the VPS host drives cold loads at its pod IP, and the restart count, termination reason, dmesg and cgroup counters decide pass or fail. The lowest passing rung sets the request and twice it the limit, written as an ADOPTED line that plan 04 copies into the base Deployment's MEASURED comment. The issuer edit travels as one pushed commit through Flux's edge Kustomization, and a certificate snapshot before and after shows whether anything re-issued.

Output: the ladder record and runbook entry, the issuer edit (or a recorded skip), the solver record.
</objective>
