How the scenario commit reaches main (DECISION Q6). `git push origin <sha>:refs/heads/main` sends every ancestor origin lacks, and plan 06 leaves its live record, summary and state commits unpushed, so pushing commit A by SHA alone would carry them too and the push would not be model-only:

| Approach | Pros / Cons | Why picked |
|---|---|---|
| Picked (Q6 1): flush first (push the planning-only commits still local, which starts neither workflow), then make commit A on a tip equal to origin/main and push it by explicit SHA, before the evidence and docs commits | Pro: the pushed range is exactly commit A, so its run is the literal positive case of criterion 1 (a push that changes only the model runs the site workflow), plus a second observed Flux roll; the flush is one more observed negative control. Con: two pushes, one more site run and rollout. | The user's choice in plan 06; it makes "alone" true by emptying the range, not by the push command. |
| One push carrying the pending records and commit A | Pro: one push. Con: the range holds .planning paths too; the site run still starts, but the push is not model-only, and the plan's own MODEL-ONLY check would stop it. | Rejected. |
| Commit A cherry-picked onto origin/main on a side branch and pushed from there | Pro: no flush push. Con: commit A gets a second SHA, local main diverges from what was pushed and needs a merge later; the evidence would cite a commit that is not on local main. | Rejected. |
| Keep everything local (Q6 2) | Pro: no outward action. Con: the model-only push clause stays pending for a push event. | Followed only if chosen. |

## Non-obvious trade-offs
- **State invalidation:** steps validate against nothing in the model (only participants are checked), so the evidence file is the only tie to the workflow and manifests; a later edit to the workflow can stale a step without failing any check. Line cites make that findable, not caught.
- **Edge labels:** steps are not relationships, so `ci -> dockerhub` as a step adds no logical relationship and cannot merge a deployment edge to `[...]`.
- **Docs drift:** the eighth namespace, the fourth hostname and the second delivery workflow make three doc statements false; the memory note on infra diagrams going stale is why the Mermaid diagrams' gap is written down rather than left silent (their retirement is out of scope, user decision 2026-10-27).
- **Pending, not passed:** a clause that has no observation yet (the src-only control under Q4 1) is recorded as pending with its reason, and the `PHASE STATUS:` line names it, so the verifier cannot read the gate as fully observed.
- **Context budget:** the estimate is 104k against a 100k budget, about 4k above it, added by the flush push and the gate's nine pair lines. The re-slice would be a separate gate plan, which would need its own tracer and whose only input is records this plan already reads; that costs more context than it saves, so the plan stays one unit and the overrun is stated here. Accepted by orchestrator, iteration 2: a 4k overrun at low confidence, in a plan whose gate task only reads records; not split.
- **Red and green, per clause:** the gate pairs each live clause with the record line where it failed (plan 06's BASELINE lines, plan 01's dev-server control, the negative pushes against the model-only push) or says AFTER-ONLY and why (a regression control whose failing case would break a live host; a before-state that does not discriminate). A clause is never paired on reasoning alone.
</tradeoffs>
