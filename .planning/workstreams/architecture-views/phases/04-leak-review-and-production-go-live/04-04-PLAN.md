## Approaches considered (project directive: decided before this PLAN.md)

How the certificate moves to production (D-08):

| Approach | Pros / Cons | Why picked |
|---|---|---|
| Picked: edit `issuerRef.name` in place, one commit, reconciled by Flux | Pro: a documented re-issuance trigger (the Secret's issuer annotation stops matching); the old staging Secret keeps serving until the new one is written; one production order. Con: Ready alone can read True on the old Secret, so the check needs the revision, the annotation and the served issuer. | D-08; research "Don't Hand-Roll". |
| Delete the Secret or run `cmctl renew` by hand | Pro: immediate. Con: a hand edit outside Git; deleting the Secret drops TLS until issuance and spends an order just the same. | Rejected. |
| A second Certificate object on the production issuer, then swap the route | Pro: staging stays untouched until the swap. Con: two commits, a second Secret, and the route edit; the flip stops being one commit. | Rejected: contradicts D-08. |

When the docs gain the link:

| Approach | Pros / Cons | Why picked |
|---|---|---|
| Picked: a docs-only commit after Ready, pushed with plan 05's push | Pro: no link ever points at a certificate warning; the flip commit stays one commit. Con: the docs reach origin one push later. | ROADMAP planning note for PUB-06. |
| Docs in the flip commit | Pro: one push. Con: a failed issuance would leave public links to a warning page, and the flip would no longer be one change. | Rejected. |

## Non-obvious trade-offs
- **Rate limit.** Let's Encrypt allows 5 certificates per exact set of names per 7 days with no override, and 5 failed authorizations per name per hour (letsencrypt.org/docs/rate-limits, updated 2026-08-05). The plan spends one order and never loops; a revert to staging costs nothing at production.
- **Permanence.** A production certificate puts the hostname into Certificate Transparency logs for good. The hostname is already in the public repository; `robots.txt` with `Disallow: /` asks crawlers to stay away and is not access control.
- **Hook cost.** The flip commit edits a k8s manifest, so it runs the full four-minute hook (Docker must be up).
- **Flux race.** Flux bump commits land on main after every image; the push procedure merges only fluxcdbot commits beneath and pushes an explicit SHA, never `--force`, and the tag is re-checked after that fetch.
</tradeoffs>

<objective>
With the owner's authorization and the reviewed tag still live, move the architecture site's Certificate to letsencrypt-production in one commit, verify the trusted certificate from the cluster and from outside, then link the public address from the README and INFRA_ARCHITECTURE.md.

Data flow in three sentences: the flip commit reaches main, Flux's apps-architecture Kustomization applies the Certificate with the new issuerRef, and cert-manager sees the Secret's issuer annotation no longer match and orders a certificate from the production ClusterIssuer through the ClusterIP HTTP-01 solver. When the order completes, cert-manager rewrites Secret architecture-tls in place, and Traefik, whose IngressRoute already names that Secret, serves the trusted chain on the next handshake. The docs commit made after Ready waits locally for plan 05's push.

Output: the flip commit, the docs commit, the decisions and the flip record.
</objective>
