## Approaches considered (project directive: decide before any PLAN.md)

Data flow in three sentences: `sync.mjs check` parses every YAML document under `<root>/k8s` once into plain objects and derives fact sets from them (defined namespaces, workloads, and, from plan 02, placements). It loads the LikeC4 computed model of `docs/architecture/model` and derives the matching sets from it (namespace-node titles, instance parents, metadata keys, drawn instances). Each rule compares one pair of sets and appends a named line to `problems`; any line means exit 1, a missing or unparseable fact source means exit 4, missing tooling means exit 3.

**Approach A (picked): extend `sync.mjs` with YAML-parsed fact readers, a small kustomization namespace resolver, and rules against LikeC4's computed model; prove each rule with a scratch-copy drill.**
**Approach B: render the manifests with `kubectl kustomize` (or a kustomize binary) and read namespaces from the rendered stream.**
**Approach C: keep regex readers (widen the current line regex in `workloads()` to `namespace:` and `targetNamespace:` lines), no new dependency.**

| Approach | Pros / Cons | Why picked |
|---|---|---|
| A: `yaml.parseAllDocuments` readers + kustomization `namespace`/`resources` walk inside `sync.mjs` | Pro: one seam, no binary download, sees block scalars and comments correctly, ~30 lines for the resolver, measured 1.08 s per check. Con: re-implements the two kustomize fields that matter (namespace inheritance through `resources`), so exotic kustomize features (components, replacements) are not followed, nor is a Flux Kustomization's spec.targetNamespace (A10); adds one npm dependency. | User-locked D-04 (yaml) and D-03; research prototyped it on the real repo with red and green output. |
| B: `kubectl kustomize` render | Pro: exact kustomize semantics. Con: a pinned kubectl download in the hook and CI, seconds per overlay, network or cache state in a check that runs in about a second; ARCHITECTURE N3 already rejected it. | Rejected: cost and a new fact-source dependency for two fields the repo uses. |
| C: regex over YAML lines | Pro: no dependency. Con: matches the comment `-n kube-system` in helmchartconfig.yaml, reads inside Helm `valuesContent` block scalars, cannot follow kustomization inheritance, and already misses keys after `labels:` (ARCHITECTURE G4). | Rejected by D-04 and by measurement. |

Sub-decisions inside A:

| Approach | Pros / Cons | Why picked |
|---|---|---|
| Placement as per-element set equality (manifest namespace set of the element's anchor documents equals the set of its instances' namespaces), skipping elements with no k8s anchor | Pro: catches one instance moved into the wrong namespace (criterion 2). Con: Phase 2 elements must carry a `workload` or `k8s/` `source` anchor to be checked. | Planner assumption A1 (research prototype, not a user decision); rated costly below. |
| Placement as "instance parent title is a defined namespace" | Pro: simpler. Con: passes a moved instance, so criterion 2 cannot be met. | Rejected. |
| Missing fact-source directory exits 4 | Pro: the hook already prints "did not run to completion" for any status other than 0 and 1, so a broken fact source is never reported as model drift. Con: one more documented exit code. | Assumption A3; exit 1 would make the hook advise "Update docs/architecture/model", which is wrong advice. |
| Hook trigger widened to the whole `k8s` tree (plan 03) | Pro: the namespace and placement readers read all of `k8s/**`, so a typo in `k8s/overlays` or `k8s/monitoring` is refused locally, not only in CI; satisfies D-12 literally. Con: any k8s commit needs Node and the docs/architecture install (about 1 s); k8s commits already run the 4-minute Gradle gates. | Assumption A2 (research recommendation). |

## Non-obvious trade-offs
- **Performance:** check now parses about 100 documents under `k8s/**` including the large Flux `gotk-components.yaml` (measured 1.08 s for the whole prototype against 0.90 s today). The old `workloads()` re-walked the tree three times per check; the port computes it once from the shared document list.
- **Memory:** the whole k8s tree is held as plain objects for one process lifetime, a few megabytes; nothing is cached across runs.
- **State invalidation:** facts are read from the working tree at check time, never cached. The existing known hole stays: the hook reads the working tree, not the index, so an unstaged fix can mask a staged defect; CI's `likec4-model-drift` job checks the committed tree.
- **Security / supply chain:** the new dependency is exact-pinned, its integrity is locked, CI installs with `--frozen-lockfile`, and a blocking human gate approves it before install. It is loaded with a dynamic import so a missing install stays exit 3 (a static import was measured to turn it into an exit-1 stack trace the hook reports as drift).

## Planner assumptions recorded (not user decisions)
- A1 placement design above. A2 hook trigger `k8s`. A3 exit 4. A4 namespace node id equals the namespace name (`kube-system`, `flux-system`, `cert-manager`, `monitoring`); existing ids `prod`, `nonprod`, `data` are kept. A5 the OK tally line is not changed in this phase (changing it would rewrite every recorded drill section). A7 the red state on the real defect is an evidence file, never a commit (a red commit is refused by the hook and fails CI).
- A10, accepted limit, rated costly: the kustomization resolver (built for placement in plan 02) follows only a kustomize.config.k8s.io Kustomization's `namespace` through `resources`, so a directory that a kustomize.toolkit.fluxcd.io Kustomization applies with `spec.targetNamespace` is placed by its own kustomization and `metadata.namespace` values, while this plan's namespace rule still counts that string as a defined namespace. Measured 2026-10-27: none of the 9 Flux Kustomizations under k8s/flux-system sets `spec.targetNamespace` (the only string targetNamespace under k8s is the HelmRelease at k8s/platform/cert-manager/cert-manager.yaml:38). Accepted rather than modelled: no check is added for it. 01-03 Task 3 states it in the standard's Checks section, and before Phase 2 anchors an element on a directory applied by such a Kustomization, Phase 2 models the field or records that element there as not placement-checked. Plan 02 records the two sibling limits, A11 (a HelmRelease is placed by its declared targetNamespace, never its rendered chart) and A12 (elements with no anchor are not placement-checked).
