## How each kind's fields reach their command

Every field is one element of the list `string split \t` returns and is passed as `$f[N]`, one
argument that fish does not split or parse again. A column a kind does not use holds `-`, so no field
is ever empty. Paths are relative to the scratch root.

| kind | file | value | what run_drills runs |
|---|---|---|---|
| none | - | - | nothing |
| sed | path | sed expression | `sed -i --sandbox -e $f[5] $scratch/$f[4]` |
| write | path | printf format | `printf $f[5] >$scratch/$f[4]`; printf expands `\n`, so the TSV holds a literal backslash-n and no tab; a percent sign would be format syntax (none of the 7 values has one) |
| delete | path | - | `trash-put $scratch/$f[4]` (file or directory) |
| mv | path | destination path | `mv $scratch/$f[4] $scratch/$f[5]` |
| certmgr_into, lonely_into, labeldrill | - | the helper's one argument | the helper of that name, called by a literal case of the switch with `$f[5]` |

Hazards, each designed out: `|`, `$`, quotes and `\n` in a sed expression arrive as written because the
field is a variable expansion; a write value reaches printf as its format, exactly as the single-quoted
inline literal did; a tab cannot occur inside a field because tab is the separator, and the field-count
check rejects a row that has one too many; a helper value with spaces (SQL over JDBC) is one argument
because fish does not word-split variables; there is no eval, and the switch is an allowlist, so a row
cannot name a command. The rows are generated by a throwaway fish script that copies each original
quoted argument verbatim, so fish unquotes it exactly as it did inline (the first refactor's method).

## Approach and trade-offs (CLAUDE.md GSD directive)

| Approach | Pros/Cons | Why Picked |
|---|---|---|
| Kind column, one run_drills loop with a switch (picked) | Pro: every drill is data, one loop, one call; each field passes as one argument, so nothing is re-parsed; sed keeps `--sandbox`; the switch is an allowlist of eight kinds. Con: a reader learns eight kinds; a write value is a printf format; a multi-edit drill depends on the consecutive-rows rule | Picked: the user's choice, and it meets every listed hazard without eval |
| TSV of whole fish snippets, run by a loop | Pro: any drill fits, no kinds to learn. Con: a snippet must be parsed as fish (eval, fish -c or source), which the brief forbids; fish quoting comes back inside the data; each snippet calls sed itself, so `--sandbox` is no longer enforced in one place; a data row becomes arbitrary code | Not picked: it brings back the re-parse the first refactor removed |
| Leave as is (15 TSV rows, 6 sed_drills calls, 21 written blocks) | Pro: no risk, already byte-identical. Con: keeps the repetition the user objected to | Not picked: the user asked for the refactor |

Non-obvious choices inside the picked approach:

1. Multi-edit drills are consecutive rows. D11 (two seds) and D12b (three seds on two files) become 2
and 3 sed rows; a row whose drill and title equal the row above continues that drill, so it gets no
header and no fresh copy. The alternative, a helper per multi-edit drill, would be the written-out
blocks again under another name.
2. The three helpers stay as kinds. Expanding certmgr_into into write and sed rows would copy its
8-line certmgr.c4 text into both D16 and D16b and lose the comments saying why the element is linked
and where the title merges; as kinds, each control still differs from its drill by one value.
lonely_into's argument-less call becomes the value unlinked, which is behaviour-identical: the helper
tests only for linked.
3. D5 and D8b are pinned to the file their find picks today, so neither needs a helper. D5 ran `find
… -path '*controller*' | head -1`, unsorted, so the file depends on directory order; it becomes an mv of
src/main/java/com/vrudenko/kanban_board/controller/BoardController.java (the first find result in the
repo tree at planning) to RenamedController.java in the same directory. Its output does not depend on
which controller moves, because the model cites the controller directory, not a file
(docs/architecture/model/model.c4 line 28, generated.c4 line 62). D8b ran `find … | sort | head -1`,
which is AppAccessDeniedException.java; it becomes a sed row on that file. Consequence: both are now
deterministic across filesystems, and if either file is renamed in the real tree the replay prints the
mv or sed error and cmp fails, where find would silently have picked another file. The rejected
alternative was two helper kinds keeping the find behaviour that no output depends on. The brief
allowed helpers here; pinning is this plan's choice and the SUMMARY must say so.
4. The table is read whole, not with `while read`. Inside a `while read` loop every command in the
body (node, sed, a helper) shares the table as stdin and could swallow rows. Reading it by command
substitution before the loop means string split always receives its argument, so the stdin hang the
first refactor's missing-id guard prevented cannot happen; the guard is adapted into four exit-2
checks (missing or empty table, wrong field count or empty field, unknown kind, split drill).
5. Not a literal `git mv`. sed_drills reads the four-column file until Task 2, so Task 1 creates
drills.tsv and Task 2 removes sed-drills.tsv with `git rm`. Git records no rename either way; it
infers one from content at diff time, and every row gains a kind column, so the end state is the same
as a `git mv`.

Performance: none worth measuring; the 36 `node sync.mjs` runs dominate (84 s for the full replay at
planning). Memory: the table is 40 short lines held in one list.

Data flow, in three sentences: drill.fish defines fresh, run and the three helpers, then calls
run_drills once with drills.tsv. run_drills reads every data row into a list, splits each on tabs into
drill, title, kind, file and value, and when the drill and title differ from the row above it calls
run for the previous drill, prints the `== drill: title` header and makes a fresh scratch copy. The
switch then applies the row's edit, and after the last row one more run prints that drill's check
result exactly as a written-out block did.
