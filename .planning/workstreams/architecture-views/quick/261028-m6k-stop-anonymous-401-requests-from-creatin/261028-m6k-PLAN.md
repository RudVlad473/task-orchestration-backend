<objective>
Stop a refused anonymous request from creating a Spring Session. Today a cookie-less request to a
protected route that gets a 401 writes a spring_session row (plus a SPRING_SECURITY_SAVED_REQUEST
attribute) and sends a JSESSIONID Set-Cookie whenever its Accept header does not name
application/json, on GET and POST alike (measured in
.planning/workstreams/architecture-views/phases/02-model-completion/02-04-401-measure.txt, rows B,
D, E; 10 more requests gave 10 more rows, each living 10800 s).

Purpose: an unauthenticated client can currently grow spring_session without limit, and every row
holds a serialized copy of the refused request. After this plan a refusal issues no SQL and sets no
cookie, whatever the Accept header or method.

Output: one config line plus comment in SecurityConfiguration.securityFilterChain, one
parameterized test (8 cases) in AuthorizationGatingTest.NoSessionSweep, red and green evidence files,
one commit. Test first: the test is proven red against the unfixed code before the fix exists.
</objective>

<data_flow>
How the data moves, in three sentences (CLAUDE.md "GSD Execution Directives"):

1. A cookie-less request to a protected route fails authorization, and
   ExceptionTranslationFilter.sendStartAuthentication calls requestCache.saveRequest before
   ProblemDetailAuthenticationEntryPoint writes the RFC 7807 401.
2. The cache in place today is RequestCacheConfigurer's default HttpSessionRequestCache, whose
   matcher skips only JSON, XHR, multipart, event-stream and favicon requests (no GET-only guard,
   because CSRF is disabled), so for any other Accept it calls request.getSession().setAttribute,
   and Spring Session JDBC turns that into INSERT SPRING_SESSION plus INSERT
   SPRING_SESSION_ATTRIBUTES and a Set-Cookie.
3. Setting a NullRequestCache as the chain's shared RequestCache makes saveRequest a no-op, so the
   refusal never touches the session. Signin is unaffected, because AuthenticationController creates
   its session through sessionAuthenticationStrategy.onAuthentication and
   securityContextRepository.saveContext and never goes through the request cache.
</data_flow>

<alternatives_considered>
Every claim about Spring Security below comes from the 6.5.11 sources jars in
~/.gradle/caches (spring-security-config and spring-security-web, the versions the app
resolves), read on 2026-10-28, plus the Spring Security reference "Prevent the Request From Being
Saved" (fetched through Context7).

| Approach | Pros/Cons | Why Picked |
|---|---|---|
| A. `http.requestCache(cache -> cache.requestCache(new NullRequestCache()))` on securityFilterChain | Pro: one DSL line, and it is the documented idiom. It sets the shared RequestCache object directly (RequestCacheConfigurer lines 88-90), and that object is exactly what ExceptionHandlingConfigurer.getRequestCache hands to ExceptionTranslationFilter (lines 257-263). It covers every Accept, every method and every route on the catch-all chain. Con: RequestCacheAwareFilter stays in the chain as an O(1) no-op. A future redirect-back login flow would have to choose a cache deliberately. | Picked. Nothing replays a saved request (evidence above), so saving none is exact. |
| A'. `http.requestCache(RequestCacheConfigurer::disable)` | Pro: also removes RequestCacheAwareFilter. Con: it is correct only because disable() is overridden to set a NullRequestCache shared object first (RequestCacheConfigurer lines 93-97). Without that override, ExceptionHandlingConfigurer falls back to a plain `new HttpSessionRequestCache()` whose matcher is AnyRequestMatcher (HttpSessionRequestCache line 53), which saves EVERY request, JSON included: a failure worse than the bug. | Rejected in favour of A's explicit shared object. The two behave the same today, and the test's JSON control rows would catch the fallback either way. |
| B. Keep HttpSessionRequestCache but restrict it: a narrower RequestMatcher, or setCreateSessionAllowed(false) | Pro: keeps a replay path. Con: nothing reads that path, so every saved request is a dead write. A matcher keeps the defect for whatever it still matches. createSessionAllowed(false) stops new rows but still serializes the request into any session that already exists (HttpSessionRequestCache line 72), for example a pre-deploy anonymous row. More code with no reader. | Rejected |
| C. Change sessionCreationPolicy on securityFilterChain | NEVER does not fix it: SessionManagementConfigurer swaps in NullRequestCache only for STATELESS (lines 387-391), and HttpSessionRequestCache keeps createSessionAllowed = true (line 51). STATELESS does fix it, but it declares the chain that owns the session-backed signin, the two-session ceiling and fixation rotation to be sessionless. That is far wider than the bug and misdescribes the API. | Rejected |
| D. A `@Bean RequestCache` returning NullRequestCache | Pro: one bean. Con: RequestCacheConfigurer.getBeanOrNull (lines 125-140) applies it to every chain in the context (managementSecurityFilterChain, resetEndpointFilterChain). That is harmless today, since both are STATELESS and already get a NullRequestCache, but it gives a one-chain decision global scope, out of sight of the chain definition. | Rejected |

The other two chains need no change: managementSecurityFilterChain and
NonprodResetSecurityConfiguration.resetEndpointFilterChain are both STATELESS, so
SessionManagementConfigurer.init already gives them a NullRequestCache.
</alternatives_considered>

<tradeoffs>
Non-obvious performance, memory, security and state trade-offs:

- **Write amplification removed.** Before the fix, each anonymous non-JSON request cost BEGIN,
  INSERT SPRING_SESSION, INSERT SPRING_SESSION_ATTRIBUTES and COMMIT, plus a Java-serialized
  DefaultSavedRequest. The live row count grows linearly with anonymous request rate times 10800 s
  (1 request/s gives about 10,800 live rows), with no per-client bound, and Spring Session's cleanup
  DELETE works over that growing table. After the fix a refusal issues no SQL, the same as the JSON
  rows A, C and F in 02-04.
- **Confidentiality.** DefaultSavedRequest copies every request header except If-None-Match and
  If-Modified-Since, plus every cookie and parameter (DefaultSavedRequest lines 123-140). An
  anonymous request's Authorization header, third-party cookies and query string therefore sat in
  spring_session_attributes for up to 180 minutes. After the fix nothing is stored.
- **Time complexity.** saveRequest becomes a no-op. RequestCacheAwareFilter still runs once per
  request, and NullRequestCache.getMatchingRequest returns null in O(1). No new per-request database
  or session lookup.
- **State invalidation: rows written before deploy.** The fix deletes nothing. Existing anonymous
  rows expire through Spring Session's cleanup job no later than 10800 s after their last access.
  Clients stop sending the cookie after its 600 s Max-Age, so the rows are no longer touched. A
  client that re-presents one within those 600 s still gets the 401, and NullRequestCache writes
  nothing into it, though Spring Session may still update its last-access time. There is no
  migration and deliberately no DELETE: none is needed, and changing production data is outside this
  quick task.
- **Ceiling and lifetimes unchanged by construction.** Anonymous rows have a NULL principal_name, so
  they were never counted by SpringSessionBackedSessionRegistry toward MAX_CONCURRENT_SESSIONS. The
  fix touches no session property: server.servlet.session.cookie.max-age stays 600 and
  spring.session.timeout stays 180m.
- **Session fixation.** Before the fix an anonymous client held a real session id ahead of signin,
  which ChangeSessionIdAuthenticationStrategy rotates at signin (AuthenticationTest.SessionFixation).
  After the fix no pre-authentication session exists. That leaves no new exposure and one fewer
  object to rotate.
</tradeoffs>
