## Approach decision (project rule: alternatives, trade-off matrix, non-obvious trade-offs)

### Facts measured at planning time (2026-11-16)

- osv-scanner v2.7.1 is still the latest release (published 2026-11-09). `gh release view v2.7.1 --repo google/osv-scanner
  --json assets` gives the asset digest `sha256:fb7dab19a8bd9bbe5c3189f09d4b7ee1820c9553a23bac202648a56efd2f6ee8` for
  `osv-scanner_linux_amd64` (58,187,936 bytes), and the `osv-scanner_SHA256SUMS` line for that file holds the same value.
  The release reports `isImmutable: false`, so the tag could be re-pointed. The SHA-256 pin is what protects the job.
- The Trivy pin exists once, at `scripts/trivy-scan.sh` line 67 (`TRIVY_IMAGE=`, 0.76.2 by digest). At HEAD,
  `bash scripts/trivy-scan.sh image-ref` prints the usage line and exits 2, which is the baseline for the new mode's gate.
- The measured recipe (005 PLAN and COMPARISON, Reproduce step 5): `./gradlew --no-daemon bootJar` took 42s with a warm
  cache. Trivy `rootfs --format cyclonedx --pkg-types library --skip-version-check --timeout 30m` over a directory holding
  the jar took about 5m45s, almost all of it a 954 MiB Java DB download, and left a 1.5 GB cache. Then came
  `osv-scanner scan source -L <file>.cdx.json --format json --all-packages --all-vulns --output-file <file>`. The SBOM's
  filename must end `.cdx.json`. osv-scanner exits 0 with no findings, 1 with findings, and 127, 128 or 129 when the scan
  failed.
- Gradle verification mode: gradle.properties sets only `org.gradle.jvmargs=-Xmx768m`, so the build verifies strictly by
  default. The Dockerfile's build stage runs `./gradlew bootJar` from an empty Gradle home with no flag, and deploy.yml
  builds that image with docker/build-push-action (newest successful deploy.yml run: 43723457306, 2026-11-15). A cold
  bootJar under strict verification therefore already passes on every deploy. trivy-scan.yml has never run on GitHub
  (`gh run list` is empty).
- `gradlew` is tracked as 100755, so no chmod step is needed. Python 3 with PyYAML 6.0.3, yq v4, unzip, shellcheck and
  Docker are on this machine. actionlint and zizmor are not.
- Baselines at HEAD: `python3 scripts/verify-comments.py check` reports `OK: 345 files, 1349 comment blocks`.
  `shellcheck scripts/trivy-scan.sh` exits 1 on one SC2012 info finding, and `shellcheck -S warning scripts/trivy-scan.sh`
  exits 0. No file among README.md, docs/INFRA_RUNBOOK.md, docs/ARCHITECTURE.md, .gitignore, scripts/trivy-scan.sh and
  .github/workflows/trivy-scan.yml contains `osv`. docs/ARCHITECTURE.md lists no scanner (no trivy, dependency-check or
  security-scan anywhere in it), so it stays unchanged.
- The comment lint (docs/CODE_STYLE.md rule 14) covers `.sh`, `.py` and `.yml`, including `run:` block scalars in
  `.github/workflows/`. It bans quick-task ids such as `261116-0pl`, `Task N`, `Phase N`, decision ids and threat ids.
  A block of 4 or more prose lines must open with a summary of at most 2 lines, and long narration sits behind
  `Decisions:` or `Known holes:`.
- Sibling action convention: first-party actions use major tags (`actions/checkout@v5`, `actions/setup-java@v5`,
  `actions/upload-artifact@v4`, `gradle/actions/wrapper-validation@v6`), and only secret-carrying third-party actions are
  SHA-pinned. trivy-scan.yml and security-scan.yml set workflow-level `permissions: contents: read`. Each guard's selftest
  runs inside its own workflow, not in invariant-checks.yml.

### Alternatives considered

1. **Picked: runner-built boot jar, Trivy rootfs SBOM, verified osv-scanner binary, Python guard.** A new
   `scripts/osv-scan.sh` does all of it. It downloads osv-scanner and checks the pinned SHA-256 first, then runs
   `./gradlew --no-daemon bootJar` and `dependencies --configuration runtimeClasspath`, then the measured Trivy rootfs
   command with the image taken from `bash scripts/trivy-scan.sh image-ref`, then osv-scanner on the SBOM. A stdlib guard
   checks coverage. The workflow sets up Java the way security-scan.yml does.
2. **CycloneDX Gradle plugin SBOM.** Apply `org.cyclonedx.bom` in build.gradle and scan its runtimeClasspath BOM.
3. **Image SBOM.** `docker build` the Dockerfile as trivy-scan.sh's image mode does, then Trivy
   `image --pkg-types library --format cyclonedx` on the result.

Excluded by the brief rather than weighed: gradle/verification-metadata.xml as input (the user chose the SBOM; 54 of
its 57 findings were outside runtime scope), and any third-party action to install or run osv-scanner (the March 2026
trivy-action tag hijack, GHSA-69fq-xp46-6x23, is why this repo runs scanners from pinned artifacts).

### Non-obvious trade-offs

- **Runner time and disk.** Trivy's Java DB (954 MiB download, 1.5 GB unpacked) lands in the container's ephemeral
  `/tmp/trivy-cache`, as in trivy-scan.sh, and is not cached with actions/cache. The cron is weekly and GitHub evicts
  caches unused for 7 days, so most runs would start cold anyway (security-scan.yml records the same observation).
  A 1.5 GB entry would also compete with the NVD cache under the 10 GB repository limit. Gradle uses setup-java's gradle
  cache. Timeouts come from the local measurement (3x, rounded up to 5 minutes), not from a runner measurement.
- **Gradle verification mode.** No flag at all. Strict verification is the default, verification-metadata.xml covers
  runtimeClasspath and the plugins, and the Dockerfile's cold `./gradlew bootJar` passes it on every deploy. The executor
  settles it again by running the script locally with no flag and by citing the newest successful deploy.yml image
  build. Lenient or off modes would run unverified artifacts inside the build, so they are never an option.
- **Binary download trust.** The release is mutable, so the version tag alone proves nothing. The SHA-256 pin was equal
  on 2026-11-16 to the SHA256SUMS line and to GitHub's asset digest, though both share GitHub as their root of trust.
  It is checked before chmod, and before the multi-minute Gradle and Trivy steps, so a tampered asset fails in seconds.
  SLSA provenance is not verified (slsa-verifier is not installed). The binary lives in a `mktemp -d` directory outside
  the checkout and outside Trivy's mount, and a trap removes it.
- **Container mount.** The Trivy container mounts only `.osv-reports/`, which is narrower than trivy-scan.sh's
  whole-checkout mount, so the scanner never sees `.git` or the sources. `persist-credentials: false` matches
  trivy-scan.yml anyway.
- **What "clean" means.** osv-scanner matches exact Maven coordinates. On 2026-11-16 it could not see 151 Spring
  (CVE, artifact) pairs that OSV holds only as git ranges, 52 pairs with no OSV record, or the 22 DOMPurify CVEs bundled
  in swagger-ui. A clean osv run therefore never clears dependency-check, and the docs must say so.
- **Information disclosure.** Public Maven coordinates go to api.osv.dev. The job references no secret.
- **Guard cost.** It is linear in roughly 150 packages and 160 tree lines, stdlib only, and finishes in milliseconds.
- **Shell choice.** The driver is bash, not fish (the global preference for new scripts), for four reasons. The runner
  has no fish. The sibling scanner script is bash. shellcheck and the comment lint read `.sh` but not `.fish`. fish has no
  `set -e`, which matters in a script whose whole job is to fail loudly.

### Data flow (3 sentences)

Gradle builds the boot jar and prints the runtimeClasspath tree, and the Trivy image pinned in scripts/trivy-scan.sh
turns the jar's BOOT-INF/lib into a CycloneDX SBOM. The osv-scanner binary runs only after its SHA-256 matches the pin.
It sends the SBOM's Maven coordinates to api.osv.dev and writes every package and matched advisory to osv.json. The guard
compares osv.json with the SBOM, and the SBOM with the runtime modules that ship a jar, failing only on a coverage
shortfall, and the workflow uploads the four files and the guard's table of counts and findings.
