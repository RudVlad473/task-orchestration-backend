## Approach decision (project rule: alternatives, trade-off matrix, non-obvious trade-offs)

### Facts measured at planning time (2026-11-16)

- osv-scanner lists `gradle/verification-metadata.xml` as a supported Java input and auto-detects CycloneDX SBOMs only by
  filename (`bom.json` or `*.cdx.json`); exit code 0 means no findings, 1 means findings, 127, 128 and 129 mean the scan
  failed (general error, no packages found, OSV API failure). Source: osv-scanner docs via Context7 (docs/output.md,
  docs/scan-source.md, docs/supported_languages_and_lockfiles.md).
- Latest osv-scanner release is v2.7.1 (published 2026-11-09), with assets `osv-scanner_linux_amd64` (58,187,936 bytes),
  `osv-scanner_SHA256SUMS` and `multiple.intoto.jsonl` (SLSA provenance). slsa-verifier and cosign are not installed.
- gradle/verification-metadata.xml holds 728 `<component` entries: every configuration Gradle ever verified (build
  plugins, test, annotation processors, POM-only BOMs and parents), not only runtimeClasspath.
- Latest successful security-scan.yml run: 42634765236 (2026-11-09, commit 6c4bef8), artifact `dependency-check-report`
  unexpired until 2027-02-07. `git diff 6c4bef8 HEAD -- build.gradle settings.gradle gradle/` is empty, so that report
  describes HEAD's dependency set. Its guard table: 157 runtime modules, 168 entries, 154 top-level jars, 35 vulnerable
  entries, 302 (entry, CVE) findings, 48 unique CVE ids (NVD 290, RETIREJS 12). Of the 302: 221 are 17 Spring Framework
  CVEs repeated on 13 spring-* jars, 20 are 5 Spring Security CVEs on 4 jars, 14 are 1 OpenTelemetry CVE on 14 jars, 44 are
  22 DOMPurify CVEs on two JavaScript bundles inside swagger-ui-5.21.0.jar, 2 on kotlin-stdlib, 1 on spring-data-jpa.
- The Dockerfile's build stage runs `./gradlew bootJar` from the same sources, so a host-built boot jar ships the same
  library set as the image.
- `rm` is denied on this machine; deletion is `trash-put`. Docker, gh (authenticated), duckdb, yq, unzip and go are present.

### Alternatives considered

1. **Picked: osv-scanner release binary on two inputs, diffed against the latest CI artifact.** Download the v2.7.1 binary into
   a `mktemp -d` directory, verify it against two digests, scan gradle/verification-metadata.xml in place and a CycloneDX SBOM
   that the repo's own digest-pinned Trivy image produces (`rootfs` mode) from a host-built boot jar. The baseline is the
   newest successful security-scan.yml artifact, scoped to runtime with the repo's own `parse_tree`, and the join runs in duckdb.
2. **Fresh local baseline and a Gradle-native SBOM.** Run `dependencyCheckAnalyze` locally for a same-day baseline and apply
   the CycloneDX Gradle plugin through an `--init-script` with `--dependency-verification lenient`, so build.gradle stays
   untouched.
3. **Docker image route with a re-dispatched CI baseline.** Build the image from the Dockerfile, scan it with the pinned Trivy
   image as `image --pkg-types library --format cyclonedx`, and trigger `gh workflow run security-scan.yml` for a same-day
   dependency-check report.

### Non-obvious trade-offs

- **Scope mismatch, the largest bias.** verification-metadata.xml (728 components) covers every configuration;
  dependency-check scans runtimeClasspath only (157 modules). A raw count diff would call every test, plugin or BOM finding
  a dependency-check miss. Every osv finding is therefore split by exact group:artifact:version against the runtime set:
  inside scope, same artifact at another version (a conflict loser whose POM Gradle verified), or not on runtimeClasspath.
- **Granularity mismatch.** dependency-check attaches one CVE to every jar whose CPE matches (17 CVEs × 13 Spring jars = 221
  of 302 rows). osv attributes an advisory to the artifacts its record lists. Counts are reported both as (group:artifact,
  CVE) pairs and as unique ids, or the fan-out dominates the comparison.
- **Identifier mismatch.** All 302 dependency-check ids are CVEs. osv reports GHSA or other ids with CVE aliases, so the join
  goes through aliases. An OSV record with no CVE alias cannot appear in dependency-check, because it reads NVD only (OSS
  Index is disabled, per the security-scan.yml header).
- **Time skew.** dependency-check data is frozen at the run's NVD timestamp, while osv-scanner queries api.osv.dev live. An
  osv-only finding published after that timestamp is classed as skew, not as a matcher difference.
- **Structural blind spot.** Neither osv input sees JavaScript bundled inside a jar (swagger-ui's DOMPurify, 44 of the 302
  rows), because neither the Gradle metadata nor Trivy's jar analysis models it. dependency-check finds it through
  RetireJS and NVD CPEs. This is the main thing a replacement would lose, and the verdict must say so.
- **Information disclosure.** osv-scanner sends every package coordinate to api.osv.dev, and the OSV lookups in Task 3 send
  CVE ids. These are public Maven coordinates; no source and no secrets leave the machine. Accepted.
- **Memory and disk.** No local dependency-check (3g heap) runs. The bootJar uses the 768m daemon cap with `--no-daemon`,
  so no daemon outlives the task. Trivy downloads its Java index database into a cache under the /tmp tools directory; its
  size was not measured at planning, so the executor records it and trashes it at the end.
- **Install trust.** The release binary is checked against the release's SHA256SUMS line, against GitHub's server-side
  asset digest, and against the digest this plan recorded a day earlier. All three share GitHub as the root of trust, so
  this is integrity, not independent authenticity. `go install github.com/google/osv-scanner/v2/cmd/osv-scanner@v2.7.1`
  (sum.golang.org transparency log) would be stronger, but compiling that module graph costs minutes and well over 1 GB
  of RAM under known memory pressure. SLSA provenance verification needs slsa-verifier, which is not installed, so the
  comparison file lists it under Could not verify. The official osv-scanner container was also considered and rejected:
  the brief names checksum or go install, and the binary scans the file in place without mount plumbing.

### Data flow (3 sentences)

osv-scanner reads package coordinates from each input (Gradle's verification metadata, and Trivy's SBOM of the shipped boot
jar) and asks api.osv.dev which advisories affect those exact versions. The newest weekly CI artifact supplies
dependency-check's CPE-matched CVEs and the runtimeClasspath tree that defines which coordinates are in scope. duckdb joins
the two on (group:artifact, CVE id or OSV alias), and only the counts and classified differences reach the committed
comparison file; nothing in the build, CI, scripts or docs is written.
