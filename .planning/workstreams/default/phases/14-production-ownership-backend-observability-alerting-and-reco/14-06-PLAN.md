<objective>
Turn on Alertmanager with a Telegram receiver (prod loud, nonprod muted), route the always-firing Watchdog to healthchecks.io as the dead-man's switch, enable the default rule groups that make sense on k3s, and add the app, platform and backup alert rules; then prove a message reaches each chat and measure Alertmanager's memory.

Purpose: "someone is told when it breaks" (D-02..D-06, D-15). Every later measurement in this phase pages through this path.
Output: Alertmanager live with measured limits, PrometheusRule kanban-alerts loaded, Watchdog pinging healthchecks.io, synthetic pages confirmed.
</objective>

<data_flow>
Prometheus evaluates the chart's default rules and PrometheusRule kanban-alerts every 30 seconds and sends firing alerts to Alertmanager in the same namespace. Alertmanager groups them by alertname and namespace, routes Watchdog to the healthchecks.io webhook, info-level alerts to a blackhole, nonprod alerts to the muted chat and everything else to the prod chat, reading the token and chat ids from files mounted from a Secret on every send. If Alertmanager, Prometheus or the VM dies, the Watchdog pings stop and healthchecks.io, outside the VM, pages Telegram on its own.
</data_flow>

<approaches>
| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Chart-managed Alertmanager config in the HelmRelease values, secrets as mounted files (bot_token_file, chat_id_file, url_file), defaultRules filtered, custom rules as one PrometheusRule CR (research Finding 3, amtool-validated) | Pro: one source of truth in git; secrets never in values; operator reloads config. Con: Helm replaces lists, so routes and receivers are owned entirely here | Matches D-02 and the repo's HelmRelease-in-git pattern |
| B. AlertmanagerConfig CRs per namespace | Pro: per-namespace ownership. Con: the operator injects a namespace matcher into every AlertmanagerConfig route; node and cluster alerts have no namespace; more moving parts for one operator | Rejected for a one-person, one-node setup |
| C. Grafana unified alerting instead of Alertmanager | Pro: UI. Con: rules live in Grafana's database, not git; the dead-man's switch pattern is Prometheus-native | Rejected |

Non-obvious trade-offs:
- Helm deep-merges maps and replaces lists: `routes`, `receivers` and `group_by` here replace the chart's (including its Watchdog-to-null route), while the chart's `inhibit_rules` and `templates` survive because this file does not set them.
- Routing is on `namespace`, not `env`: only PodMonitor-scraped app series carry `env`; kube-state-metrics and node alerts carry `namespace` or nothing (node alerts therefore page the prod chat).
- Alertmanager keeps silences on an emptyDir (chart default, no storage): a restart drops silences. Accepted on one node.
- AppTargetDown only sees a pod that exists but cannot be scraped; a deleted or crash-looping pod is AppDeploymentUnavailable's job (8 minutes, longer than the 180-second startup probe plus Recreate's empty window).
- PostgresBackupMissing uses `absent()`, so it fires until the CronJob's first scheduled success is recorded; a manual Job may not set lastSuccessfulTime.
</approaches>
