<objective>
Count the two Kafka-side decisions the app already takes (a failed publish, a record sent to the dead-letter topic), add fixed latency buckets to the per-endpoint HTTP timer, and pin every app series an alert rule reads with a scrape test that spells the names exactly as PromQL does.

Purpose: the DLT counter is what turns "dead-letter messages > 0" into a page, and the buckets are what the p95 alert and the Phase 14.1 SLOs read. Split out of 14-04 so neither plan exceeds the context budget. Closes the metric half of the folded remote-logging-and-alerting todo (its alerting half lands in 14-06 and 14-08).
Output: two startup-registered Kafka counters proven at their real hooks, the SLO bucket property, and PrometheusScrapeE2ETest as the name contract with the rules.
</objective>

<data_flow>
KafkaEventPublisher increments its publish-failure counter from two hooks (the whenComplete failure branch, and a catch around the send that rethrows), and the activity listener's RetryListener.recovered increments the dead-letter counter; both counters are registered at startup in the shared MeterRegistry. The Prometheus registry renders them, with the request-path counters from 14-04 and the bucketed http_server_requests_seconds histogram, on the management port's /actuator/prometheus. The 14-06 rules query those exact series names, which PrometheusScrapeE2ETest reads back from a real scrape.
</data_flow>

<approaches>
| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Counters at the publish callback and RetryListener.recovered, registered eagerly per bounded tag value; SLO buckets by property; a scrape test asserting literal series names (research Finding 2) | Pro: counts exactly the decision the alert names; first event visible to increase(); names pinned by test. Con: two config classes gain a MeterRegistry | Matches research Finding 2 and the existing RetryListener hook |
| B. Alert on the out-of-the-box series instead (spring_kafka_listener_seconds_count with an error tag, kafka_producer_record_error_total; present per research) | Pro: no code. Con: listener errors count each retry attempt, not records dead-lettered; producer errors are per client, not per event type | Rejected: neither series names the dead-letter decision |
| C. percentiles-histogram for the HTTP timer | Pro: any quantile later. Con: about 70 buckets per uri x method x status series against 7 | Rejected: 7 fixed buckets are enough for a p95 and bound series count |

Non-obvious trade-offs:
- A counter registered lazily on its first increment is invisible to increase() for that first event (Prometheus has no prior sample), so both counters are registered at startup, and the event tag is pre-registered for every ActivityEvent record. Registration lets increase() see every failure after a pod's first scrape; a dead letter written before that scrape (the pod's first sample is already 1) is caught by the 14-06 rule's new-series branch, not by registration.
- The buckets apply to every uri the timer records; the p95 rule excludes /actuator by matcher. Management-port requests are not observed at all (Boot does not observe the management child context, pinned by 14-07's test), so the matcher is a guard against a Boot change, not a live filter.
- The scrape test is the only test that sees the Prometheus rendering (the _total suffix, the le label format); registry-level tests in 14-04 and Task 1 cannot catch a renamed series.
</approaches>
