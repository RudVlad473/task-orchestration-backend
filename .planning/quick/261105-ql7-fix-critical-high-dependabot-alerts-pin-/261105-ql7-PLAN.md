### Approaches considered

snappy-java:
- S-A. One more entry in the existing `dependencyManagement { dependencies { } }` block, next to
  lz4-java, at 1.1.10.12, plus a floor. **Picked.**
- S-B. A Gradle `constraints { implementation('org.xerial.snappy:snappy-java:...') }` block, which is
  the brief's wording.
- S-C. Bump kafka-clients (`ext['kafka.version']`) or spring-kafka to a release that asks for a fixed
  snappy.

Guava:
- G-A. Bump the direct declaration to 33.7.2, spelled `-jre`, plus a floor. **Picked.**
- G-B. Delete the declaration. The brief allows this only if Guava is unused, and it is used.
- G-C. Replace the Guava calls with JDK equivalents (`Math.toIntExact`, `List.of`, `String.split`) and
  pin only the transitive copy.
- G-D. Spell the bump `33.7.2-android`, the current flavor.

### Non-obvious trade-offs

- **The floor comparator is blind to snappy today.** verifyRuntimeDependencyFloor parses only
  `major.minor.patch`, so a 1.1.10.12 floor reads a resolved 1.1.10.5 as equal and passes. Task 1
  proves that blind spot (F1), then adds an optional fourth number, read as 0 when absent (F2 goes
  red). All nine existing floors and their resolved versions have three parts, so their verdicts do not
  change.
- **Guava's declared version is a project-wide floor.** The plugin applies the directly declared
  version to Confluent's transitive request (B2 shows "selected by rule"). Deleting the line would bring
  back 32.0.1-jre, not remove Guava. The new floor makes that a build failure.
- **Flavor switch.** On this standard-jvm build Guava 33.x resolves to the jre jar under either
  spelling. The dependency on the android jar goes away. The proof is A2's `Variant jreRuntimeElements`
  and V3's bootJar listing.
- **Capability conflicts.** Guava 33's module metadata declares the `com.google.collections:google-collections`
  capability. A module in the graph that provided it would fail resolution. None is in
  verification-metadata.xml today, and V1 catches one if it appears.
- **Native code.** snappy-java extracts a bundled native library on first use. 1.1.10.9 updated those
  libraries and fixed musl detection on glibc hosts. The production image is eclipse-temurin:21-jre-jammy
  (glibc, x86_64). Snappy loads only when a snappy batch is produced or consumed. The app never compresses
  today, but any client that can write to the topic can send a snappy batch (the internal Kafka hop has
  no SASL or TLS, per a pending todo), and that reach is what the advisories threaten.
- **Runtime compatibility.** kafka-clients 3.9.2 against snappy 1.1.10.12, and the Confluent schema
  registry client against Guava 33, are covered by the 12 kafka-tagged classes in the strict `test`
  run (K1) and by S1, a forced snappy round trip. The pre-commit hook's fastTest skips all kafka-tagged
  classes.
- **Verification metadata.** The recipe in build.gradle lines 111-121 is run with bootJar (what the
  Dockerfile builds) and `dependencies --configuration runtimeClasspath` (what Dependency Submission
  resolves) added. 261105-pay showed that the recipe can miss POMs, and only a strict cold run caught
  it, so V1 is mandatory. CI's Dependency Submission runs with verification off (261024-m86 finding),
  so the local strict run is the stronger check.
- **Scans.** OSV by coordinate is the before/after check here. OWASP dependencyCheckAnalyze is not
  run: it is network-bound and runs weekly in security-scan.yml. The build.gradle dependencyCheck comment
  said Guava "carries zero real advisories". That is now false, so Task 2 rewrites it.
- **Cost.** There are two full suite runs (write mode, then strict, about 6 minutes each), a targeted
  Kafka run and the hook (about 4 minutes) on the 8.7 GiB WSL host. Check `free -h` before each long
  run (docs/SESSION_LESSONS.md lesson 9).

### Known holes (stated, not fixed here)

- Old checksum entries for snappy-java 1.1.10.5 and guava 32.0.1 stay in verification-metadata.xml.
  Gradle's write mode adds entries and never prunes them, and the m86 bumps left lz4-java 1.10.1,
  jackson-databind 2.21.4 and tomcat-embed-core 10.1.55 the same way.
- The alerts close only after a push to main and the next Dependency Submission run. This plan never
  pushes.
- S1 runs on this WSL host's JVM (glibc x86_64), not inside the production image.
- Alerts 1 and 2 (spring-webmvc, critical, no fix for Boot 3.5) and 7 (opentelemetry-api, medium) are
  untouched.
