### Approaches considered

A. Filesystem and security context for the postgres container

1. **`readOnlyRootFilesystem: true` on the container, emptyDir at /var/run/postgresql, pod-level `seccompProfile: RuntimeDefault`.** Picked.
2. **Run as the image's postgres uid (`runAsUser: 999`, `runAsGroup: 999`, `fsGroup: 999`, `runAsNonRoot: true`).** Not picked.
3. **Container field only, and a documented exception for the StatefulSet's KSV-0118 pod row.** Not picked.
4. **A field added only to make the pod securityContext non-empty (for example `fsGroupChangePolicy: OnRootMismatch`).** Not picked.

B. The KSV-0109 false positive

5. **Path-scoped `.trivyignore.yaml` with a statement, plus `--ignorefile` in config mode.** Picked.
6. **A plain `.trivyignore` with `KSV-0109`, the form docs/INFRA_RUNBOOK.md names.** Not picked.
7. **Reword the init scripts so the rule's keywords no longer match (rename the `*_pass` variables, avoid the word PASSWORD).** Not picked.
8. **Move the init scripts out of the ConfigMap (bake them into a derived image).** Not picked.

### Non-obvious trade-offs

- **Deploy effect (Flux applies k8s/ on a push to main).** A pod-template change restarts the single replica `postgres-0`. One instance
  serves both the prod and the nonprod database, so both environments lose their database from the moment the old pod stops until the
  new one is ready; a failed start is an outage for both until the commit is reverted and Flux reconciles. The StatefulSet has no
  liveness probe and a 60 second termination grace period (stop signal SIGINT, fast shutdown). The data PVC is untouched and not
  re-initialised (measured: an existing data directory is detected and init is skipped). How the apps' connection pools recover
  after a database restart was not measured. This plan never pushes.
- **Security.** A read-only root stops a code-execution foothold in the database container from rewriting binaries or the entrypoint
  on the root filesystem. It is not an execution barrier: the container still starts as root with the default capability set (the
  entrypoint needs CHOWN, SETUID and SETGID), `/var/run/postgresql` is writable and not `noexec`, and the data volume is writable by
  design. KSV-0012, KSV-0003, KSV-0020, KSV-0021, KSV-0001 and the rest are MEDIUM and LOW findings this HIGH-only item leaves alone.
- **Seccomp.** RuntimeDefault is applied to a pod that today runs without an explicit profile. The Docker runs applied Docker's default
  profile, which containerd's RuntimeDefault is derived from, and the writable-root census run is the control for both effects; the
  cluster's own profile and any syscall Postgres makes only under load were not measured. Other pods on this node already use it.
- **Existing data directory.** The populated-volume run used a volume written by this same image digest. A data directory written by
  an older 16.x image on the node was not tested; no start-up step here depends on who wrote the files.
- **Image drift.** `postgres:16` is a floating tag. The census subject is the local image id above, which the plan never re-pulls; the
  node may hold another digest, so the entrypoint's behaviour (the chown and `mkdir` steps that tolerate a read-only root) is
  assumed unchanged across minors, not measured on the node's copy. The manifest comment carries the falsifier: an image bump repeats the census.
- **Disk-backed emptyDir.** No `medium: Memory` (the pod's 256Mi limit and the dated MEASURED memory comment must not change) and no
  sizeLimit (as in architecture-site). The directory holds a socket and a lock file of a few bytes.
- **Operator workflows.** Anything that writes into the running postgres container's root filesystem now fails (for example a dump
  redirected to a file in the pod); output has to go to stdout or the data volume. None exists in the docs or scripts today.
- **What the suppression hides.** The entry silences KSV-0109 for everything rendered into k8s-data-postgres.yaml, so a real
  credential added to a ConfigMap in that root later would not show in this report. The compensating controls are gitleaks on every
  commit (it refuses credential-shaped values) and the rule that credentials arrive through the out-of-band Secret; the statement in
  the file carries a falsifier (an init script that carries a literal value ends the exception).
- **Regression cover.** There is no new gate: the weekly report-only Trivy scan and its guard hold it, and promoting HIGH to a gate is
  the separate decision docs/INFRA_RUNBOOK.md names. Suppressed rows are absent from the guard table by design (the guard's own
  known-holes list says so), which the runbook paragraph now states next to the entry.
