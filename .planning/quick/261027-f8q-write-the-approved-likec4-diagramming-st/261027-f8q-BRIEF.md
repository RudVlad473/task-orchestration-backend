# Brief: the approved LikeC4 diagramming standard, with verification outcomes

Task: write the approved standard into `docs/DIAGRAM_CONVENTIONS.md`. Only what survived verification
is written as standard; what failed is written as "not adopted" with its reason. The user approved
the design below on 2026-10-27 after reading it in chat. Evidence for every row in "Verification"
lives next to this file in `verify/` (scripts, result files, rendered PNGs).

## Approved design

Diagrams are one LikeC4 model (spike 006, `.planning/spikes/006-likec4-model-of-this-app/model/`)
with one viewpoint per Kruchten view. The survives-a-refactor test in the existing doc stays the
inclusion test: nothing class-level.

### Entities and rules

- **Element**: a runtime thing with identity. Kinds are a closed set: `actor`, `system`, `container`,
  `component`, `thread`, `datastore`, `table`, `topic`, `job`.
- **Relationship**: a runtime interaction between two Elements, kind `sync` or `async`, labelled with
  a protocol-level fact.
- **Deployment node** (`server`, `cluster`, `namespace`) and **Instance** (an Element placed on one
  node via `instanceOf`). prod and nonprod are two Instances of one Element, not two copies. Instances
  inherit all logical relationships, so the physical view re-draws no edges.
- **Viewpoint**: logical, process, development, physical, scenarios. Each View belongs to exactly one.
  A View projects Elements and never owns one.
- **Provenance**, exactly one per fact: `generated` (written from code, never edited), `checked`
  (hand-written, carries `metadata` a script compares with the code), `authored` (hand-written,
  unverified). Prefer moving a fact up this ladder; an authored relationship is said to be authored.
- Kinds say what a thing is. Tags are only for cross-cutting facts (`generated`, `planned`, one per
  Viewpoint).
- **Numbers in labels** (retry counts, schedules, ceilings) are either covered by a check or left out.
- **Every physical node carries its CPU architecture in its title** (the `technology` field does not
  render on deployment nodes, measured in spike 006).
- An `index` context view is the landing page and sits outside the 4+1.

### Viewpoints

| Kruchten view | LikeC4 construct | Represents | Does not represent | Provenance |
|---|---|---|---|---|
| Logical | plain `view` over `table` elements | tables and the FK ownership chain | columns, entity classes, DTOs | generated (see V4); framework-owned tables authored |
| Process | `view ... of kanban` | request threads, named executors, topics, consumer groups, DB writes | method calls, class names | topics checked; executors and groups authored |
| Development | `view ... of kanban`, packages as `component` | top-level packages and their dependency direction | classes, third-party libraries | edges generated from imports (see V5); no cycle rule |
| Physical | `deployment` model and `deployment view` | servers (arch in title), cluster, namespaces, workloads | pods, replicas, secrets, the monitoring stack (excluded, as in `production-host.mmd`) | workloads checked against `k8s/base` and `k8s/data`; nodes authored |
| Scenarios | `dynamic view`, one per outcome | client-visible facts: method and path, status and `code`, cookie, SQL action, topic | internal calls | authored |

The Logical row bends the old doc ("rarely needed"): it earns a place because every fact in it is
generated, so it costs no upkeep.

Branching: the old `signin.mmd` has `alt` branches in one picture. The standard is one dynamic view
per outcome (signin-ok, signin-bad-credentials, signin-ceiling), because one trace is one Kruchten
scenario. It costs several views instead of one.

### Checks (the drift script, spike 007 `sync.mjs`)

Proven in spike 007: validate, generated file up to date, topic set vs `KafkaTopics.java`, workload
set vs `k8s/base` and `k8s/data`, every `metadata.source` path exists. Drills: 4 of 4 drift kinds
caught; a renamed controller class is not caught, by design.
Not built, proposed by this standard: an unknown-metadata-key check (see V2), a "every view has a
viewpoint tag" check, a "every `server` node title names an architecture" check.

## Hazards found while preparing

- `scripts/verify-diagrams.py check` fails on a `dangling-reference` when a doc names a `diagrams/`
  path that does not resolve. The new section must not name a path under `docs/diagrams/` that does
  not exist; describe the planned layout without that prefix, or point at the spike path.
- The existing doc's inventory table and rules describe the seven Mermaid diagrams and stay true
  until they migrate. Add the LikeC4 section; do not delete or rewrite the Mermaid sections.
- The Avro question from the proposal is open and not part of this change: 14 `.avsc` files exist
  while `application.properties` says "5 event types". Neither is verified.
