## Non-obvious trade-offs

- **State invalidation.** generated.c4 is a cache of code facts, invalidated by byte comparison. After T3
  any Java change that adds or removes a cross-package import invalidates it. The hook does not list
  src/main/java as a trigger, so such a commit passes locally and CI's `likec4-model-drift` job fails on
  push (invariant-checks.yml runs on every non-docs path, lines 22 to 33). Adding the trigger would make
  Node and a per-worktree pnpm install a prerequisite of every Java commit; that cost is not taken. T3
  records the hole in the hook's "Known holes" comment and T6 in the standard.
- **Performance.** `check` gains a walk of every file under src/main/java and a model about twice the size
  (17 elements today, about 33 after T3). T3 times `check` before and after and records both figures; a
  slowdown past 2x is reported, not hidden.
- **Silent misattribution.** A regex that attributes an FK to the wrong table draws a wrong edge that
  validates. T2 cross-checks the generated FK set against the information_schema result in
  `.planning/quick/261027-f8q-write-the-approved-likec4-diagramming-st/verify/fk-result.txt`, and T3
  cross-checks the import edges against a fresh run of that folder's `pkg.fish`.
- **Drill safety.** sync.mjs reads its model from its own folder. A drill that edits a view would edit the
  real model, and an interrupted run would leave it edited. T1 adds `--model DIR`, and every drill works
  on a scratch copy.
- **`--seq` is global.** It applies to every dynamic view in the export. All three dynamic views are
  sequence views by decision, so nothing else is affected.
- **Security and memory.** No new package enters: the install is frozen against the existing lockfile
  (likec4 1.60.0, audited VERIFIED in quick task 261027-fuj). Each task commit runs the real hook, so
  gitleaks scans every staged diff. The commit's bounded wait can kill a hung hook, which can orphan
  Testcontainers containers (no Ryuk on this host), so P4 checks `docker ps -a` after every commit.

## Data flow

sync.mjs reads the migrations, KafkaTopics.java, the k8s manifests and, after this change, the Java
import lines; `generate` renders those facts into model/generated.c4, and `check` re-renders and
byte-compares that file, then loads the whole model through LikeC4 to test topics, workloads, sources and
viewpoint tags. The pre-commit hook runs `check` when a staged path is a fact source or the model, CI runs
it on every non-docs push, and the drills and the self-test mutate scratch copies to prove each rule can
fail. `likec4.fish png` renders every view from the same model, drawing dynamic views as sequence diagrams.

## Decisions taken in this plan

- **Numbers removed, not checked.** The standard allows either. A check per number would need a regex per
  Java or YAML construct plus a drill and a self-test case each, for three labels. The values stay in the
  code; T5 removes them from the model and records each source line in its claims file.
- **Package-edge drift is caught in CI only** (see State invalidation above).
- **Three signin views, as the standard names them.** `signin-bad-credentials` traces the unknown email.
  A wrong password returns the identical 401 body right after the SELECT by id that `signin-ceiling`
  draws, so its SQL actions are a prefix of that view and nothing is undrawn. The description says so.
- **The 400 VALIDATION_FAILED branch of signin.mmd is not a view here.** It never reaches the database and
  belongs to the error-status-split scenario, which the todo places outside this change.
- **Structural edges get their own kinds.** `sync` and `async` stay the runtime kinds. Foreign keys are
  kind `fk` and package dependencies kind `imports`, both generated. If the parser rejects either name as
  a keyword, use `foreignKey` or `packageImport` and record which.
- **The `job` kind.** The standard's closed kind set (docs/DIAGRAM_CONVENTIONS.md, Entities and rules)
  lists `job`, but spec.c4 does not declare it and the backup CronJob is a `system`. Found while
  planning; T5 aligns the model to the approved standard (two lines).
- **One commit per task, each through the real hook.** Every task leaves the tree green, so each is its
  own commit. Without Java changes Gradle's `spotlessCheck` and `fastTest` are usually up to date (they
  were in 261027-fuj), so a run takes well under the 4-minute worst case.
