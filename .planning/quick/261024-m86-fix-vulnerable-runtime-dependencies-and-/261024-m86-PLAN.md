Trade-offs that are not obvious:
- Performance: GitHub evicts a cache unused for 7 days, and the cron is weekly, so most Monday runs on
  main will start cold. Main also cannot read caches saved by branch runs. The timeouts are therefore
  sized from a measured COLD run, not a warm one. Each run saves one ~125 MB cache entry (10 GB repo
  cap, LRU eviction).
- Memory: the scan steps raise the Gradle daemon heap for CI only, overriding gradle.properties'
  768m from the command line. Local builds are unchanged.
- State: a cache key that never changes is immutable, which is why the current single key would
  have restored the same August database forever. The new key is unique per run, restored by prefix.
  A partial or failed update is not saved, because dependency-check records the NVD last-modified
  marker only when an update completes, so a partial database gives the next run nothing to resume
  from and could hold a half-written H2 file.
- Security: the dependency-submission job holds contents: write while Gradle executes third-party
  plugin code. It gets job-scoped permissions, checkout without persisted credentials, no shared
  cache, and verification left strict. The NVD key could appear in --info output, so tee'd logs go to
  RUNNER_TEMP and are never uploaded (GitHub masks the step log; it does not mask artifact files).
- Fail-safe direction: skipTestGroups = false means that if scanConfigurations is ever emptied, test
  configurations get scanned too. The scan becomes noisier, not blinder.
- Override hazard: an ext version property outlives the BOM it overrides. Under a Spring Boot 4 BOM,
  tomcat.version = 10.1.x would force Tomcat 10 onto a Tomcat 11 stack. Each override carries a TODO
  linking PR 16, and the runtime floors catch the opposite silent failure, a misspelt property name
  that changes nothing.

Data flow (3 sentences): The scan job restores the newest NVD cache by prefix, runs
dependencyCheckUpdate alone and saves the refreshed database before analysis starts, writes the
runtimeClasspath module tree, then runs dependencyCheckAnalyze, which now scans runtimeClasspath's
resolved jars because the test-name heuristic no longer excludes it. The guard compares the JSON
report's dependency count against the tree's module count, fails below 95 percent, and prints the
counts and severities to the log and the job summary. Separately, dependency-submission resolves
runtimeClasspath and posts that graph to GitHub's dependency submission API, which matches it
against advisories continuously for Dependabot alerts on main.
