## Approaches considered (project directive: alternatives and trade-off matrices)

What the dashboard check requests:

| Approach | Pros/Cons | Why picked |
|---|---|---|
| A. API form `/api/public/dashboards/<id>`, 200 plus `"publicDashboardEnabled":true` | Pro: a wrong or revoked id answers 404, Traefik's 503 and a login redirect fail on status; same route as the README link. Con: 198 KB per check of VM Host Metrics; proves the share resolves, not that panel queries return data | Picked: the only form whose answer depends on the share existing (measured) |
| B. README page form with an HTML marker | Pro: the exact URL a reader clicks. Con: a wrong id answers 200 with the same Grafana shell; the only discriminator is undocumented boot data | Rejected on measurement |
| C. Both forms | Con: doubles requests for no failure B can see that A cannot | Rejected |

Alerting mechanism:

| Approach | Pros/Cons | Why picked |
|---|---|---|
| A. Separate job, `gh` with the job token, issues: write only | Pro: no secret, no third-party action, the probe job keeps no scope, a broken alert step cannot turn the probe red. Con: one extra job per run (about 10 s) | Picked (user design item 2) |
| B. A step inside the probe job | Con: the probe job would need issues: write, and its exit code would mix outage and alert failures | Rejected |
| C. Alertmanager, or a third-party issue action | Con: Alertmanager is disabled in-cluster and dies with the cluster it watches; an action adds supply-chain trust for what `gh` already does | Rejected |

Passing the verdict between jobs: job outputs (a few hundred bytes, no storage, no retention, no
upload or download action) over an artifact (two extra actions, retention and a download step for one
line of state) or re-probing in the alert job (two verdicts that can disagree).

Repeated failures: a comment per failing run (picked: each run's evidence lands in the thread and the
path is observable in the test) over a silent body edit (no notification, history lost) or a
comment only when the failure set changes (needs prior state parsed from comments). Cost: one
notification per failing run while the issue is open, bounded in practice by the measured 2.6-8.2 h
schedule cadence.

Making the failure path testable:

| Approach | Pros/Cons | Why picked |
|---|---|---|
| A. Permanent boolean input drill: adds a fixed known-wrong dashboard URL | Pro: repeatable fire drill of the real path; accepts no text, the URL lives in the file, only users with write access can dispatch; the worst misuse is a drill issue the next passing run closes. Con: a drill emails the owner | Picked: the alert path had never run (last 100 runs green) and must stay testable |
| B. Temporary commit that breaks one URL, then a revert | Con: two throwaway commits with the 4-9 minute hook on a branch headed for main | Rejected |
| C. String input for an override URL | Con: lets a dispatcher point the probe anywhere and write arbitrary text into an issue | Rejected (the brief forbids arbitrary URLs) |

No committed selftest for the probe: the defect lived in the real route and the real issue API, and
the drill exercises exactly those; a committed fixture-server test would test curl against a
simulation (global rule: code is a liability). The offline replay below is a one-off proof.

SHA-pin scope: only the job holding a write-scoped token (picked, user design item 3) over pinning
every non-GitHub action (rejected without the user: deploy.yml holds an explicit risk acceptance) or
none (rejected: the security review's gap is real).

Non-obvious trade-offs: the alert job's concurrency group serializes alert jobs, and GitHub cancels a
superseded pending one, which shows that rare run grey; job-level `!cancelled()` instead of
`always()` keeps a manually cancelled run from touching issues; the alert latency is the real
schedule cadence, hours on this repo.
