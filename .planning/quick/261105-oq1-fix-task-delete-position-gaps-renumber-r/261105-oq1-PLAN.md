<objective>
Close the position gap `TaskService.deleteById` leaves, so the sibling-count probe in `TaskService.save`
never hands a new task a position another task already holds, per the user's chosen approach:
renumber after delete with one bulk UPDATE (decrement every position greater than the deleted one in
that column). Check `SubtaskService.deleteById` for the same bug (finding: subtasks have no position,
see "Findings" below).

Purpose: the source todo (`.planning/todos/pending/2026-11-01-task-delete-leaves-position-gaps-so-a-later-create-can-dupli.md`)
records that a middle delete followed by a create duplicates a position, which breaks the
"contiguous from zero" invariant that `save`, `moveToColumn`'s clamp and the learning docs all assume.

Output: a failing-then-passing service test, the one-call fix, a query-count guard proven against a
per-row mutant, an updated `deleteById` Javadoc, the learning docs and the sibling todo brought in line,
one commit.

Core data flow (3 sentences): `DELETE` reaches `TaskService.deleteById`, which loads the task through
the ownership-verified chain and captures its column id and position before deleting its subtasks and
the task. In the same transaction one bulk JPQL UPDATE decrements the position of every task in that
column whose position is greater than the deleted one, so the delete and the renumber commit or roll
back together. A later create reads the sibling count, which again equals the next free slot.
</objective>

## Design record (required by .claude/CLAUDE.md before a PLAN.md is approved)

The user chose the approach; this records the alternatives and why.

**Alternatives considered**

1. **Renumber after delete, one bulk UPDATE (CHOSEN).** Capture the deleted task's position, then call
   the existing `TaskRepository.shiftPositions(deletedColumnId, -1, deletedPosition + 1, Integer.MAX_VALUE)`.
   It is the exact pattern `ColumnService.deleteById` already uses for columns (line 265), so no new
   repository query is introduced.
2. **Create takes max(position) + 1 (REJECTED by the user).** One line in `save`, but gaps persist. Gaps
   break `moveToColumn`, which treats the sibling count as the index space: with positions
   `0,1,2,4,5,6,7`, a same-column "move to end" of the task at 7 clamps to `count - 1 = 6`, shifts the
   task at 6 up to 7, and lands the moved task second-to-last.
3. **Full-column rewrite with a window function (REJECTED).** A native `UPDATE ... FROM (SELECT id,
   row_number() OVER (ORDER BY position, id) - 1 ...)` that rewrites every row in the column. It would
   also heal pre-existing gaps and ties, but it is native SQL beside a JPQL twin that already exists,
   rewrites every sibling (not only the later ones) on every delete, and is the only place the
   ordering rule would live in SQL instead of JPQL.

**Trade-off Matrix**

| Approach | Pros/Cons | Why Picked |
|---|---|---|
| Renumber after delete (bulk shift) | Pro: invariant holds after every mutation; reuses `shiftPositions` and the column-delete precedent; one statement regardless of sibling count. Con: one extra UPDATE per delete writing k rows (k = tasks after the deleted one); does not repair gaps already in stored data | Picked by the user; matches `ColumnService.deleteById`; keeps `save` and `moveToColumn` correct without touching them |
| Create uses max(position) + 1 | Pro: one-line change, no extra write on delete. Con: gaps persist; `moveToColumn`'s count-based clamp misplaces a move-to-end; the "contiguous from zero" comment in `save` stays false | Rejected: fixes the duplicate symptom, leaves the broken invariant that move relies on |
| Full-column ROW_NUMBER rewrite | Pro: self-heals existing gaps and ties. Con: native SQL, rewrites all n rows per delete, second home for the ordering rule | Rejected: heavier per delete; healing old data is a separate decision (see Open questions) |

**Non-obvious trade-offs**

- **Performance.** Exactly one more prepared statement per delete, constant in sibling count (pinned
  by the query-count test). Rows written are O(k), each an MVCC tuple plus WAL. `tasks.column_id` has
  no index (V1-V9 create none; learning doc 01 "Known gaps" records it), so the UPDATE's WHERE is a
  sequential scan of `tasks`, the same cost class `countByColumnId` and `findAllByColumnId` already pay
  on every create and list.
- **@Version and stale persistence-context entities.** Plain JPQL `update` does not bump `@Version`, so
  shifted siblings keep their version: a client editing a sibling's title is not 409'd because another
  task was deleted. This is the decision `moveToColumn`'s Javadoc already records for moves. Bulk JPQL
  bypasses the persistence context, but the only `TaskEntity` managed in this transaction is the
  deleted one (plus its EAGER column/board/user chain and its subtasks), and the shift range starts at
  `deletedPosition + 1`, so no managed entity can go stale; no `flush()`/`clear()` is needed (unlike
  `deleteAllByColumn`, which may run inside a caller's multi-column loop). Hibernate auto-flushes the
  pending task DELETE before a bulk update on the same table; either statement order is correct
  because the range excludes the deleted row.
- **Atomicity.** The DELETE carries `AND version = ?`; if another request updated the task after this
  one loaded it, the DELETE matches 0 rows and the whole `@Transactional` method rolls back, shift
  included. The shift must therefore stay inside `deleteById`'s transaction: no `REQUIRES_NEW`, no
  async step.
- **Concurrency race (pre-existing, not closed here).** Under READ COMMITTED a create that reads the
  count while a delete is uncommitted takes position n, the delete then closes its gap to n-2, and the
  column ends with a gap that the next create turns into a duplicate. Two concurrent creates already
  duplicate today (accepted as T-06-19; `TaskRepository.findAllByColumnId`'s `(position, id)` sort keeps
  reads deterministic). Closing it needs a per-column lock in every mutation; out of scope.
- **Security.** The shift's column predicate is the whole access boundary of that statement:
  `TaskRepository.shiftPositions`'s Javadoc warns that without it the UPDATE renumbers every user's
  tasks. The column id must be the one read from the ownership-verified task (CODE_STYLE rule 2),
  never a path variable (see the separate todo on ignored nested-URL parent ids).

  `mockColumns` are empty columns on the same board.

  deferral is resolved.

## Open questions (not planned; surfaced to the user)

- **Existing stored gaps.** The fix stops new gaps but does not repair columns that already hold gaps or
  ties from earlier deletes. In such a column the next create can still duplicate a position (count no
  longer equals max + 1). Repair would be a one-shot Flyway migration renumbering each column by
  `(position, id)`. Not planned: it changes production data on deploy and the user has not asked for it.
- **Concurrent mutation race** (see Non-obvious trade-offs): candidate for a todo, not this plan.
