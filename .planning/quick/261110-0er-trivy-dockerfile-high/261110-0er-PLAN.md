### Approaches considered

1. **Upgrade only apt and libapt-pkg6.0 in the runtime stage, and run as the numeric nobody user.** Picked.
2. **Bump the base image to `eclipse-temurin:21-jre-noble`.** Not picked.
3. **Remove apt and libapt-pkg6.0 from the image.** Not picked.
4. **A dedicated uid created with `useradd` instead of nobody.** Not picked.

### Trade-off matrix

| Approach | Pros / Cons | Why Picked |
|---|---|---|
| 1. `apt-get install --only-upgrade apt libapt-pkg6.0` then `USER 65534:65534` | + Measured today: the simulated upgrade touches exactly 2 packages and the candidate equals Trivy's FixedVersion. + One small layer, same OS and same Java build. + The nobody user needs no `useradd` layer and matches the backup image. - The build now reaches archive.ubuntu.com, a new build-time dependency (CI has no layer cache, so it runs on every build). - The layer becomes dead weight once the base ships the fix, and only a comment says so. | Smallest change that removes exactly the findings named, with evidence for both halves. |
| 2. Base `21-jre-noble` | + Fixes by moving, no custom layer. - Changes the production OS, glibc and OpenSSL; the whole dpkg set and the MEDIUM and LOW findings change, none of it measured. - Whether noble's apt carries the same CVE was not checked. - `scripts/trivy-scan.sh` and the guard cite the jammy base. | Blast radius far larger than a two-package patch, and unmeasured. |
| 3. Purge apt and libapt-pkg6.0 | + Findings vanish and the image loses its package manager. - `dpkg --purge --force-depends` leaves broken dependency records in the dpkg database. - Removes the tool the next OS CVE fix needs. - Hides the finding by deletion instead of fixing it. | Trades a measured fix for a trick that makes the next patch harder. |
| 4. `useradd` uid 10001 | + A uid no other nobody-owned file or process on a node shares. - Adds a `groupadd` and `useradd` layer and needs a matching uid in a manifest the sibling owns. - A numeric uid with no passwd entry gives the JVM an odd `user.name` and `user.home`, not measured. | The pod mounts no volume a shared uid could reach, so the isolation buys nothing here. |

### Non-obvious trade-offs

- **Numeric USER, on purpose.** kubelet can only verify `runAsNonRoot: true` against a numeric image user; a user name makes it
  refuse to start the container. `65534:65534` keeps the sibling item free to set `runAsNonRoot`.
- **The jar stays root-owned and 0644.** No `--chown`, so a compromised JVM cannot rewrite the code it runs. The app needs no
  writable path besides /tmp, which is 1777 in the base.
- **Read-only root filesystem is the sibling's likely next step.** The Tomcat temporary directory and the JVM perf-data file
  live in /tmp, so a `readOnlyRootFilesystem: true` in app.yaml would need an emptyDir at /tmp. Task 2 measures this with
  `docker run --read-only` and hands the result to 261110-0es through the proof file. It is evidence, not a manifest edit.
- **Deploy effect.** The first push after this commit rebuilds and publishes the production and nonprod tags from one build,
  and Flux then rolls both environments to an image whose process is uid 65534. The pod strategy is Recreate, so a crash on
  start is an outage until a rollback. This plan never pushes; the owner of the push decides.
- **Trivy's database is not pinned.** A new HIGH CVE on another package may appear between planning and scanning. If it does,
  it is reported by name in the proof file and is not fixed under this item.
- **Cost.** The image scan includes a Gradle build inside `docker build` (about 4 to 8 minutes) plus about 2 minutes of scan.
  Task 1 builds once for the probes; its build context is made equal to the scan's so the second build can reuse the Gradle
  layer. That reuse is an expectation, not a guarantee.
