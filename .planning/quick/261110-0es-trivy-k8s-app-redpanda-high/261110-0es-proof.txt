== Not verified (no cluster was available)
- kubelet emptyDir semantics: mode 0777 and fsGroup group ownership versus Docker tmpfs and named volumes (the Redpanda run used a 0777 tmpfs and the app run a 1777 tmpfs and a copy-up volume).
- seccomp RuntimeDefault on top of the dropped capabilities: the Docker runs mirror cap-drop ALL and no-new-privileges but not the seccomp profile.
- The real rollout: the app Deployment under Recreate (a gap with no pod) and the single-replica redpanda StatefulSet restart, in both kanban-prod and kanban-nonprod.
- A live PVC that the previous container (writable root) already wrote: the read-only runs used fresh data volumes, only a restart was exercised on the read-only volume.
- A crash writing to the now read-only /var/lib/redpanda/coredump; Redpanda's crash behaviour on a read-only root was not measured.
- Behaviour under real traffic: the app's Kafka producer path and real user sessions were not driven; only /actuator/health and /api/healthz.
- The schema registrar when Redpanda is still starting (the runs waited for a healthy broker first).
- The Redpanda image was the same v26.2.1 for both app images; the app image tags in the cluster (main-165-ef59a17 today) were the ones run, with the broker config of the base manifest but Docker-style advertise addresses (redpanda:19092), not the StatefulSet DNS names.
Push consequence: a push of the manifest commit lets Flux re-apply k8s/, which replaces the app pod (Recreate, so a gap) and restarts redpanda-0 in kanban-prod and kanban-nonprod. A crash on start is an outage until a rollback.
