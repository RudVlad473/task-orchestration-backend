### Approaches considered

1. **Read-only root on all three containers, with an emptyDir only where a census shows a write.** Picked.
2. **Documented exception for redpanda: keep its root writable and add one unrelated field only to clear KSV-0118.** Not picked.
3. **An init container that seeds /etc/redpanda from the image's redpanda.yaml into an emptyDir (the pattern in Redpanda's own Helm
   chart).** Not picked.
4. **emptyDir with `medium: Memory` for /tmp and /etc/redpanda.** Not picked.

### Trade-off matrix

| Approach | Pros / Cons | Why Picked |
|---|---|---|
| 1. `readOnlyRootFilesystem: true` plus emptyDir at /tmp (app) and /etc/redpanda (redpanda) | + Clears all 8 rows with 2 fields and 2 volumes; Trivy dry run on a scratch copy took HIGH 4 to 0 with nothing new. + The Redpanda mount is backed by a measured read-only run, not a doc claim. + Same shape as two existing manifests. - A cluster was not available, so kubelet emptyDir semantics are inferred from Docker tmpfs. - /tmp stays writable and executable. | The only option that removes the findings without hiding them, and every added mount is measured. |
| 2. ### Non-obvious trade-offs

- **Deploy effect (Flux applies k8s/ on a push to main).** A pod-template change restarts pods: the app Deployment (strategy Recreate)
  loses its only pod before the new one starts, and the redpanda StatefulSet (1 replica) restarts redpanda-0, in both kanban-prod and
  kanban-nonprod. The app's register-schemas init container waits on Redpanda's schema registry and a failing init blocks the pod, so if
  both roll together the app comes up only after the broker does. The data PVC and fsGroup 101 are untouched. This plan never pushes.
- **Security.** A read-only root stops a code-execution foothold from rewriting binaries or config on the root filesystem; for the
  image prod runs today (root, jar owned by root) it is the main protection of /app/app.jar. It is not an execution barrier: /tmp is
  writable and not `noexec`, so a dropper can still run from there. Capabilities, privilege escalation and runAsNonRoot on redpanda are
  other findings (MEDIUM and LOW) that this HIGH-only item leaves alone, so the 22 MEDIUM and 46 LOW rows stay as measured.
- **Memory and disk.** A disk-backed emptyDir has no sizeLimit here, as in architecture-site: a runaway writer would fill node disk
  instead of being capped, and a sizeLimit would instead evict the whole pod when crossed. The writes are small (Tomcat temp
  directory, JVM perf-data file, one 1 KB config file). It does not touch the pod's memory request.
- **Crash dumps.** `/var/lib/redpanda/coredump` sits on the root filesystem and becomes unwritable. rpk's coredump tuner is off in the
  image's config and Redpanda's own crash reports go to the data directory on the PVC, so nothing is known to write there; what a
  crash would do was not measured.
- **Hidden default file.** The emptyDir at /etc/redpanda hides the image's default redpanda.yaml. Measured identical output today with
  the pinned v26.2.1; a future image that reads the default file for something rpk does not rewrite would behave differently.
- **Regression cover.** There is no new gate: the weekly report-only Trivy scan and the guard hold it, and promoting HIGH to a gate is
  the separate decision docs/INFRA_RUNBOOK.md names. A new invariant in verify-k8s-invariants.py would fail on the postgres roots until
  the sibling item lands.
