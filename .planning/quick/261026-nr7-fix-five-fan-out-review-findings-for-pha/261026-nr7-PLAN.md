## Unit A: the Kafka publish path (BUG-1, BUG-3, BUG-5)

`application-test.properties`, `KafkaClusterIdLookupBoundE2ETest`, new tests.

### BUG-1: a full publish pool drops events uncounted

When `kafkaPublishExecutor` rejects a task, the `@Async` proxy throws before `onActivityEvent` runs, so
nothing is counted (verified: Claude's 300 boards, 82 uncounted; `TaskRejectedException` in 108 of my own
`fastTest` result files).

### BUG-3: a failed send takes about 4s

Verified by me: 4139, 4016 and 4015 ms. The 2s admin cluster-id lookup runs on every send while the broker
is down, then the producer waits `max.block.ms` 2s.

### BUG-5: the test profile leaves the admin client at the 2s production bound

### Approaches considered

BUG-1:

| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. A `RejectedExecutionHandler` on the executor that counts and logs | Pro: no change to the publisher. Con: the handler receives only a `Runnable`, never the event, so it cannot tag the counter with the event class or log `eventId` and `boardId` | Rejected |
| B. Drop `@Async`; the after-commit listener submits to the executor itself and catches `TaskRejectedException` with the event in hand | Pro: counts under the right tag and logs the ids; no `CallerRuns` (which would block the caller). Con: the listener now runs on the caller's thread for the cost of one submit | Picked |

BUG-3:

| Approach | Pros / Cons | Why picked |
|---|---|---|
| A. Turn observation off on the template | Pro: removes the lookup. Con: loses the trace propagation that 14-07 exists to deliver | Rejected |
| B. Override the template's protected `clusterId()` with a negative cache: after a failed lookup, skip lookups for 30s | Pro: keeps tracing; a send costs the 2s producer bound except one probe per 30s. Con: a small extra class; sends in the backoff window carry no cluster id attribute | Picked |

The cache is a tiny class with an injectable clock so its logic is tested without Kafka.

### Non-obvious trade-offs

- Dropping `@Async` changes where `onActivityEvent` runs. `ContextPropagatingTaskDecorator` stays on the
  executor, so the trace still crosses to the pool thread.
- The 30s window is a judgement, not a measurement.
- Raising the producer bound is out of scope.
